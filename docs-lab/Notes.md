## Start > 概要

次のサブタイトルは良くありません。

> OpenSpecは、コードが書かれる前に、あなたとコーディングエージェントに共有可能な、レビュー可能な計画を提供します。

プランモードが一般化した現在では強い価値提案にならず、それ以前にOpenSpecの魅力を十分に伝えられていないと思います。

OpenSpecは、単一セッションの計画を共有するためだけのものではありません。より大きな機能開発を軌道に乗せ、関係者の認識を揃え続けるためのものです。

重視している点：
- チームで利用できること
- Gitネイティブであり、成果物をバージョン管理へコミットできること
- 意図した振る舞いと実装された振る舞いが一致すること
- 意図した振る舞いを記録し、実装との一致を保てるよう支援すること
- 正確さと一貫性を保つこと

制御理論からの着想：

制御理論の説明では、システムが現在の状態を測定し、目標と比較し、その差を小さくするよう動作を調整する過程を分解して示します。

## Guides > アイデアを探索する

このセクションでは、以下の点を言及すべきだと思います。

この機能は問題空間を探索し、重視する問題を見極めて深く掘り下げるためのものです。

問題空間を自由に探索し、さまざまなアイデアや論点を行き来できるようにするという、ほかのスキルとは異なる思想で設計されています。

SuperpowersやMatt Pocockのskillsなど、最近登場した同分野のツールと似た役割を果たします。

exploreと組み合わせて使われる例もよく見かけます（組み合わせ先は要追記）。

多くの場合、これはユーザー体験と個人の好みの問題です。エージェントと認識を揃えるための唯一絶対のスキルや方法はありません。

思慮深い設計パートナーと対話する形を好む人もいれば、問題を十分に理解できるまで質問を受ける形を好む人もいます。

exploreスキルは、必要に応じて自由にカスタマイズできます。

ドキュメントとは無関係な点：

PMが抱える問題をどう解決するか？
PMに適した居場所をどう用意するか？ PMが果たしたい役割は何か？
その役割を効率よく果たせるよう、どう支援するか？

- PMは基本的に、それをチケットへ変換しているのか？

今週中に何を完了させるか？

- spec driftエージェント？
- ダッシュボード？

- エージェントのセッションとトレースをより有効に活用する方法を検討する。

## docs-lab執筆時のメモ（2026-08-19、project-configページ）

ドキュメントではなく製品側の問題：このリポジトリにインストール済みのスキルが、現在のテンプレートより古くなっています。`.claude/skills/openspec-archive-change/SKILL.md`には`openspec instructions`の呼び出しがまったくありませんが、`src/core/templates/workflows/archive-change.ts:40`では呼び出すよう指示しています。インストール済みのapplyスキルも、読み取るJSONの`context`/`operationGuidance`フィールドに言及していません。そのため、設定内容はCLI出力まで渡るものの、古いスキルはそれを利用するようエージェントへ指示しません。`openspec update`を実行すれば更新されるはずです。

## docs-lab執筆時のメモ（2026-08-19、schemasページ）

スキーマシステムの検証中に見つけた製品側の問題（ファイル参照はすべて現時点のもの）：

- `schema init`の「次のステップ」に、実在しない形式のコマンド`Use with: openspec new --schema <name>`が表示される（`schema.ts:999`）。実際の構文は`openspec new change <name> --schema <name>`。
- `openspec new change`のスピナーが、解決されたスキーマではなくハードコードされたデフォルトスキーマを表示する（`new-change.ts:118`）。`Creating change 'x' with schema 'spec-driven'...`に続けて`Schema: lite`と表示される。
- `schema fork`が`schema.yaml`を再シリアル化するため、リテラルの`instruction: |`が折り返し形式の`>`へ変わり、コメントも削除される。結果として、forkとupstreamの差分に不要な変更が大量に現れる（`schema.ts:706-712`）。
- すべての`openspec schema`サブコマンドと`openspec schemas`/`templates`は`process.cwd()`を使用し、`--store`を受け付けない。ルート解決を行うほかのコマンドとは異なり、サブディレクトリから実行すると何も検出しない（`schema.ts:383/485/634/768`）。
- `suggestSchemas`という「もしかして」を提示するあいまい検索ヘルパーは存在するが、どこからも利用されていない（`project-config.ts:420`）。

ドキュメント側のフォローアップ：コミュニティスキーマカタログは旧`docs/customization.md`の`#community-schemas`にしかなく、`customize/schemas.md`からGitHub上の同ファイルへリンクしている。旧ドキュメントツリーを廃止する際は、このカタログの移行先をdocs-lab内に用意する必要がある。
