# クイックスタート

> 既存のリポジトリで、最初の変更提案をアイデアからアーカイブまで進める。

始める前に、マシンへ CLI を[インストール](installation.md)し、プロジェクトで OpenSpec を
[セットアップ](setup.md)してください。

## ループの全体像

すべての変更提案は、同じ 5 つのステップで進みます。エージェントとアイデアを検討し、エージェントが
計画を下書きします。コードを書く前に計画を修正し、その計画からエージェントが実装します。
最後にアーカイブすると、完成した内容で仕様が更新されます。

```mermaid
flowchart LR
    explore["1 · Explore<br/>一緒に検討する"] --> propose["2 · Propose<br/>エージェントが計画を下書きする"]
    propose --> review["3 · Review<br/>計画を修正する"]
    review --> apply["4 · Apply<br/>エージェントがタスクごとに実装する"]
    apply --> archive["5 · Archive<br/>変更内容を仕様へ反映する"]
    archive -. "次の変更提案" .-> explore
```

以下のプロンプトはすべて、コードを依頼するときと同じ AI チャットへ入力します。どのプロンプトも
OpenSpec スキルを名前で呼び出し、その表記はどのツールでも同じです。通常の文章で
「レート制限を追加する変更提案を作成して」と依頼することもできます。一部のツールには、
より短いコマンド別名があります。Claude Code では`/opsx:propose`を使用し、
[ほかのツールでは表記が異なります](../reference/supported-tools.md)。

## ステップ 1：Explore

計画を依頼する前に、エージェントとアイデアを検討します。AI チャットへ次を入力します。

```text
/openspec-explore このアプリでレート制限をどのように機能させるべきか
```

Explore は検討のためのモードです。エージェントがコードベースを調査し、重要な質問を投げかけ、
選択肢を整理して前提を問い直します。コードもファイルも書きません。アイデアを明確にすることが成果です。

問題の整理に必要なだけ、このモードで検討を続けます。方向性が固まったら、次へ引き継ぎます。

```text
/openspec-propose
```

この行を入力すると、決めた内容を引き継いで Propose が開始されます。ステップ 2 の最初のプロンプトは省略してください。

## ステップ 2：Propose

Propose は、アイデアをレビュー可能な計画へ変換します。Explore から引き継いだ場合は、すでに開始されています。
最初から変更内容が明確な場合は、AI チャットで直接依頼します。

```text
/openspec-propose レート制限を追加する
```

エージェントは必要な内容を確認した後、変更提案フォルダを作成します。

```
openspec/changes/add-rate-limiting/
├── proposal.md    変更の理由と内容
├── specs/         「完了」の条件を、テスト可能な要件として記載
├── design.md      技術上の判断（変更提案に必要な場合だけ）
└── tasks.md       実装チェックリスト
```

この時点ではコードを書きません。Propose は計画を作成したところで停止します。

## ステップ 3：計画をレビューして修正する

まだ文章だけで何も実装されていないうちに、計画を修正します。次の順序で確認してください。

- **`proposal.md`**：取り組むべき問題か、適切な規模かを確認します。
- **`specs/`**：最も重要な確認対象です。この要件を満たせば完了と判断できるかを確認します。
- **`tasks.md`**：仕様を過不足なく網羅しているかを確認します。

修正方法は 2 つあります。

- 自分でファイルを編集します。アーティファクトは通常の Markdown ファイルであり、ファイル自体が計画です。
- 「仕様に未認証の場合がない」など、問題点をエージェントへ伝えます。エージェントがアーティファクトを修正します。

## ステップ 4：Apply

Apply は計画をコードへ変換します。実装はコンテキストが空のほうが進めやすいため、
新しいチャットセッションを開始してください。AI チャットへ次を入力します。

```text
/openspec-apply-change add-rate-limiting
```

エージェントは変更提案フォルダを読み取り、`tasks.md`を順に実装します。完了したタスクにはチェックを付けます。

- **中断した場合やコンテキストが足りなくなった場合**：新しいセッションを開き、もう一度 Apply を依頼します。最初の未完了タスクから再開します。
- **計画に誤りが見つかった場合**：ステップ 3 のいずれかの方法でアーティファクトを修正し、Apply を続けます。
- **進捗**：`tasks.md`のチェックボックスに記録されます。隠れた状態はありません。

## ステップ 5：Archive

アーカイブでは 2 つの処理を行います。変更提案の要件で本仕様を更新し、変更提案フォルダを
アーカイブフォルダ（`/openspec/changes/archive/*`）へ移動します。

`tasks.md`のすべての項目にチェックが付いたら、AI チャットへ次を入力します。

```text
/openspec-archive-change add-rate-limiting
```

アーカイブの処理を順に見ていきます。

```file-steps
## 完了した変更提案
> 実装は完了しています。差分仕様（この変更提案が追加する内容）はまだ変更提案フォルダ内にあり、specs/ にはレート制限がまだ反映されていません。
  openspec/
  ├── specs/                                   （rate-limiting 仕様はまだない）
  └── changes/
      └── add-rate-limiting/
          ├── proposal.md
          ├── tasks.md                         すべてチェック済み
          └── specs/
              └── rate-limiting/
                  └── spec.md                  差分：ADDED 要件

## 要件を specs/ へ反映
> 差分内の各要件を本仕様へ反映します。追加要件は追記し、変更要件は以前の版を置き換えます。新しい機能には新しい仕様ファイルを作成します。
  openspec/
  ├── specs/
+ │   └── rate-limiting/
+ │       └── spec.md                          「Requirement: Rate limiting」を追加
  └── changes/
      └── add-rate-limiting/
          └── specs/
              └── rate-limiting/
                  └── spec.md                  マージ元となる差分

## フォルダを archive/ へ移動
> 差分を含む変更提案フォルダ全体を、日付の接頭辞を付けてアーカイブへ移動します。何も削除しません。
  openspec/
  ├── specs/
  │   └── rate-limiting/
  │       └── spec.md
  └── changes/
-     └── add-rate-limiting/
+     └── archive/
+         └── 2026-08-08-add-rate-limiting/
+             ├── proposal.md
+             ├── tasks.md
+             └── specs/rate-limiting/spec.md

## 実装されたシステムを仕様に反映
> changes/ が空になり、次の変更提案を開始できます。specs/ はシステムの動作を示す信頼できる情報源で、archive/ はそこに至った履歴です。
  openspec/
  ├── specs/
  │   └── rate-limiting/
  │       └── spec.md                          実装どおりの仕様
  └── changes/
      └── archive/
          └── 2026-08-08-add-rate-limiting/
```

Git は別の仕組みです。変更提案フォルダをコードと一緒にコミットしても、ワークフローのほかの部分は
変わりません。PR に対していつアーカイブするかはチームの取り決めです。
[チーム](../guides/teams.md)ガイドで判断材料を説明します。
