# プロジェクト設定

> `config.yaml`に数行追加し、プロジェクトに合った方法で変更を計画させます。

`openspec/config.yaml`では、ワークフローが変更を計画する方法を指定します。

たとえば、次の設定は[tasks.md](../reference/schemas/spec-driven/index.md)アーティファクトの作成ルールを追加します。

```yaml
rules:
  tasks:
    - 各タスクの最後にコミットする
```

エージェントは実行時にこのルールを読み取り、各タスクの最後へコミット手順を加えます。

ルールは短く保ってください。ここへ書いた内容はすべてエージェントのコンテキストに入るため、冗長なルールは出力の質を下げることがあります。

## 仕組み

`config.yaml`には、エージェントがアーティファクトを作成したり、ワークフローを進めたりするときに受け取る指示を保存します。

ワークフローを実行するたびに、次の処理が行われます。

1. ワークフローを実行します（例：`/openspec-propose`）。
2. エージェントが[`openspec instructions`](../reference/cli.md)コマンドを呼び出します。
3. コマンドが`config.yaml`からコンテキストとルールを読み取ります。
4. OpenSpec の組み込み指示と独自の設定が、エージェント向けの 1 つのプロンプトにまとめられます。
5. エージェントはこのプロンプトに従ってアーティファクトを記述します。

たとえば、`context`フィールドとページ冒頭のルールを設定すると、`tasks.md`に対する[`openspec instructions`](../reference/cli.md)の出力は次のようになります。一部を省略し、注釈を加えています。

```xml
<artifact id="tasks" change="add-dark-mode" schema="spec-driven">

  <!-- config.yaml からのコンテキスト -->
  <project_context>
    技術スタック: TypeScript、Node.js
    ドメイン: EC プラットフォーム
  </project_context>

  <!-- config.yaml からの tasks に関するルール -->
  <rules>
    - 各タスクの最後にコミットする
  </rules>

  <!-- OpenSpec からの組み込み指示 -->
  <instruction>
    ...良い tasks.md の書き方...
  </instruction>

  <template>
    ...記入する tasks.md の構造...
  </template>

</artifact>
```

最初にプロジェクト設定が渡され、その後に OpenSpec の組み込み指示とテンプレートが続きます。ルールは組み込み指示へ追加され、置き換えることはありません。`config.yaml`の編集内容は、次回の実行からエージェントへ渡されます。

[ワークフロー実行](../reference/architecture/workflow-runs.md)では、呼び出しからアーティファクトの書き出しまで、実行処理全体を説明しています。

## フィールド

エージェントが受け取る内容は、3 つのフィールドで指定します。各フィールドの型、制限、検証規則は、[Project configuration (config.yaml)](../reference/configuration/config-yaml.md)を参照してください。

| フィールド   | 役割                                         | 渡される対象                                 |
| ------------ | -------------------------------------------- | -------------------------------------------- |
| `context`    | エージェントが常に受け取る指示               | すべてのアーティファクト、`apply`、`archive` |
| `rules`      | 特定のアーティファクトに対する追加指示       | そのアーティファクトの作成時のみ             |
| `operations` | ワークフローの手順をどう実行するかという指示 | `apply`と`archive`のみ                       |

`config.yaml`のほかのフィールド（`schema`、`store`、`references`）では、プロジェクトが使用するスキーマと OpenSpec ルートを選びます。詳しくはフィールド仕様のページを参照してください。

各フィールドが渡されるのは、表の最後の列に示した対象だけです。たとえば、`verify`は`rules`を受け取りません。`verify`は、作成済みのアーティファクトに対して実装を検証します。

### context

`context`には、アーティファクトの作成、タスクの適用、アーカイブを行うときに、エージェントが事前に知っておくべき情報を書きます。

```yaml
context: |
  クロスプラットフォームで提供するため、設計とタスクでは Windows、macOS、Linux を対象にする
  技術スタック: TypeScript、Node.js、Commander.js
  Conventional Commits を使用する
```

これは計画時のコンテキストであり、プロジェクトのドキュメントではありません。上記のクロスプラットフォーム対応のように、すべての計画へ影響する事実を追加します。エージェントがコードを読めば分かる情報は含めないでください。

**別の言語**：`context`はすべてのアーティファクトへ渡されるため、出力言語の変更にも使えます。たとえば、`すべてのアーティファクトをスペイン語で記述する。`という 1 行を加えると、ワークフローが生成する提案、仕様、タスクファイルがすべてスペイン語になります。

### rules

`rules`はアーティファクト ID をキーとして、特定のアーティファクトへ追加します。各行は、そのアーティファクトの組み込み指示に加えられます。

```yaml
rules:
  proposal:
    - 変更提案は 500 語以内にする
  tasks:
    - すべての UI タスクに Playwright テストを含める
```

これにより、提案は短くなり、`tasks.md`では常にブラウザテストが計画されます。ほかのアーティファクトは変更されません。

### operations

`operations`は、アーティファクトに何を書くかではなく、エージェントが`apply`と`archive`をどう実行するかを指定します。

```yaml
operations:
  apply:
    guidance:
      - タスクを完了にする前にリンターを実行する
  archive:
    guidance:
      - アーカイブ前にリリース内容を要約する
```

`apply`では、エージェントがタスクを完了にする前にリンターを実行します。`archive`では、アーカイブ前にリリース内容を要約します。

## config.yaml だけでは不十分な場合

`config.yaml`では標準ワークフローへ指示を追加できますが、アーティファクトの種類や構造は変更できません。そこまで制御したい場合や、ルールだけでは一貫した動作にならない場合は、[スキーマをフォーク](schemas.md)してください。
