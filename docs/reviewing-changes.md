# 変更のレビュー

OpenSpec の約束は、あなたと AI が **コードを書く前に何を構築するかについて合意する**ということです。この合意は、AI が草案したものを実際に読んだ場合にのみ意味を持ちます。このページは、何を開くか、どの順序で開くか、何を探すかということを 2 分間で行うためのページです。

賭け方はシンプルです。1 段落の計画で間違った方向に進むと、ほぼ無料です。 300 行のコードで同じ間違いを犯すことはありません。レビューはその賭け金を集める場所です。

## あなたが振り返る 2 つの瞬間

正確には次の 2 つがあります。

```
/opsx:propose ──► REVIEW THE PLAN ──► /opsx:apply ──► REVIEW THE CODE ──► /opsx:archive
                  (before any code)                    (/opsx:verify)
```

1. **`/opsx:propose`** の後 (または `/opsx:ff`)、`/opsx:apply` の前 — まだ言葉だけの段階で計画を読みます。
2. **ビルド後**、`/opsx:verify` を使用して、コードが計画どおりに実際に実行されたことを確認します。

最初のレビューが最も節約につながり、人々がスキップするレビューです。このページはほとんどの時間をそこで過ごします。

## この順序で読んでください

変更点は`openspec/changes/<name>/`のプレーンMarkdownのフォルダです。何か問題がある場合に最も早く終了できる順序でファイルを読んでください。

```
openspec/changes/add-dark-mode/
├── proposal.md      1. the intent and scope   ← if this is wrong, stop here
├── specs/…/spec.md  2. the requirements       ← the heart of the review
├── design.md        (only for bigger changes) — the technical approach
└── tasks.md         3. the plan of work
```

すべての行を読む必要はありません。ファイルごとに 1 つずつ、計 3 つの質問に答える必要があります。

## 提案: これは正しい問題ですか?

まず`proposal.md`を開きます。 「なぜ」と「何を」、つまり意図、範囲、アプローチを 1 ～ 2 段落で捉えます。

**良いものとは次のようなものです:** 1 つの明確な意図、あなたが認識している範囲、そしてこれを今実行する価値がある理由。

**危険信号:**

- あなたが要求した問題とは少し *異なる * 問題を解決します。
- 範囲が拡大しました。あなたはテーマの切り替えを要求しましたが、提案では「その間に」認証にも触れています。
- 曖昧ですね。 「設定ページの改善」は範囲ではありません。 「OSの設定を尊重するダークモードトグルを追加する」です。

**回答すべき質問:** *これは私が実際に求めたことと一致していますか?また、何かがこっそり入っていませんか?* 答えが「いいえ」の場合は、やめてください。これ以上読まずに、提案を修正してください ([](#pushing-back-is-cheap) を押し戻す] を参照)。

## 仕様デルタ: 「完了」は正しく定義されていますか?

これがレビューの核心です。 `specs/` の下の仕様差分には、変更が出荷されたときに何が *真実*になるかが、要件とそれを証明するシナリオとして記載されています。

```markdown
## ADDED Requirements

### Requirement: Dark Mode Toggle
The system SHALL let a user switch between light and dark themes.

#### Scenario: Respects the OS preference on first load
- GIVEN a user who has never set a theme
- WHEN they open the app on a device set to dark mode
- THEN the app renders in dark mode
```

**適切な要件とは次のようなものです:** テスターに​​渡すことができる 1 つの明確な `SHALL`/`MUST` ステートメントと、GIVEN/WHEN/THEN が実際にそのステートメントを実行する少なくとも 1 つのシナリオ。

**危険信号:**

- **曖昧な要件。** 「システムは高速でなければなりません」を構築したりテストしたりすることはできません。何が速いの？
- **シナリオのない要件**、またはその要件をテストしないシナリオ。
- **すべての中で最も貴重な発見: 何が欠けているのか。** AI は、ユーザーが *言ったこと* を忠実に書き留めます。あなたの仕事は、言い忘れたことに気づくことです。 OS 優先のケースを最も重視していて、シナリオでそれについて言及されていない場合、それはレビューの元が取れたことになります。

デルタを読んで、*システムがまさにこれだけを実行できたら嬉しいでしょうか?* ここにはまだコードに関するものは何もないので、変更するのは安価です。

## タスク: 作業計画は正気ですか?

最後に`tasks.md`を開きます。これは、AI が実行する実装チェックリストです。

**良いものは次のとおりです:** 順序付けられたステップ。それぞれのステップは要件に追跡可能であり、神秘的なものは何もありません。

**危険信号:**

- 一致する要件がないタスク (それはどこから来たのでしょうか?)。
- 1 つの巨大な「機能の実装」タスクにより、実際の決定がすべて隠蔽されます。
- 先ほど承認した範囲外のものに触れるタスク。

ここでは、見積もりや細かい管理をしているのではなく、計画がすでに受け入れた要件と一致しているかどうかを確認しているのです。

## 押し返すのは安い

3 つの質問のいずれかが間違っていた場合は、そのように答えてください。フェーズはなく、何もロックされていません。問題を修正して次に進みます。 [変更の編集](editing-changes.md):] とまったく同じように 2 つの方法があります。

- **ファイルを自分で編集します。** これはプレーンな Markdown です。スコープラインを変更し、要件を強化し、タスクを削除します。
- **何が問題なのかを AI に伝え**、修正させます。 *「認証の変更を範囲外に削除します。」* *「ユーザーが既にテーマを選択している場合のシナリオを追加します。」* *「タスク 3 をスキーマと UI に分割します。」*

次に、変更した部分をもう一度読みます。あなたが署名する計画になるまで草案を書き直します。このやり取りが「機能」しているのです。

## コードの後: 確認してください

作品が構築されたら、`/opsx:verify` が 2 番目のレビューになります。アーティファクトとコードを再読み取りし、次の 3 つの次元にわたる不一致を報告します。

|寸法 |チェック内容 |
|-----------|----------------|
| **完全性** |すべてのタスクが完了し、すべての要件が実装され、シナリオがカバーされます。
| **正確さ** |実装は仕様の意図と一致しており、エッジケースは処理されます。
| **一貫性** |設計上の決定は実際にコードに反映されます。

```
You: /opsx:verify

AI:  Verifying add-dark-mode...

     COMPLETENESS
     ✓ All 8 tasks in tasks.md are checked
     ✓ All requirements in specs have corresponding code
     ⚠ Scenario "Respects the OS preference on first load" has no test coverage
```

問題に重大、警告、または提案としてフラグを立てますが、アーカイブは**ブロックされません**。ギャップを表面化し、通話をあなたに残します。これは、「AI がコードを書いたかどうか」と「私たちが合意したものを構築したかどうか」の違いです。

`/opsx:verify` は拡張されたプロファイルにあります。お持ちでない場合は、`openspec config profile` (その後 `openspec update`) でオンにするか、変更と差分を自分で再読み込みしてください。

## レビューのサイズを適切に調整する

すべての変更が完全なパスを獲得できるわけではありません。 1 ファイルのタイプミスの修正には、20 秒の精査が必要です。認証、支払い、または回復できないデータに関わる変更には、上記のすべての質問が必要です。重要なのは決して形式的な手順的なものではなく、ミスが高くつくところには注意を払い、そうでないところには目を通すことだ。

## 2 分間のチェックリスト

- [ ] 提案の意図は私が求めたことと一致します。
- [ ] スコープには余分なものは何も入り込んでいません。
- [ ] すべての要件はテストするのに十分なほど具体的です。
- [ ] すべての要件には、それを実際に実行するシナリオがあります。
- [ ] 私が最も気になるケースがカバーされています。
- [ ] タスクは要件にマップされます。神秘的なものや範囲外のものは何もありません。
- [ ] AI がまさにこれだけを構築し、それ以上のものを構築しなければ、私は安心します。

7 つすべてが合格した場合は、自信を持って `/opsx:apply` を実行してください。たとえ失敗しても、それは挫折ではありません。2 分間がその役割を果たしているのです。
