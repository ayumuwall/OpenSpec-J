# 変更のレビュー

OpenSpec の目的は、あなたと AI が **コードを書く前に何を作るか合意する**ことです。この合意は、AI が下書きした内容を実際に読んで初めて意味を持ちます。このページでは、何をどの順序で開き、何を見るべきかを 2 分で確認する方法を説明します。

考え方は単純です。1 段落の計画の段階で方向違いに気づけば、修正コストはほぼゼロです。300 行のコードになってから同じ間違いに気づくと高くつきます。レビューは、その安い段階で間違いを拾うためにあります。

## レビューする 2 つのタイミング

正確には次の 2 つがあります。

```
/opsx:propose ──► REVIEW THE PLAN ──► /opsx:apply ──► REVIEW THE CODE ──► /opsx:archive
                  (before any code)                    (/opsx:verify)
```

1. **`/opsx:propose`** の後 (または `/opsx:ff`)、`/opsx:apply` の前 — まだ言葉だけの段階で計画を読みます。
2. **ビルド後**、`/opsx:verify` を使用して、コードが計画どおりに実際に実行されたことを確認します。

最初のレビューが最も効果的で、最もスキップされがちです。このページではそこを中心に扱います。

## この順序で読んでください

変更は `openspec/changes/<name>/` にある通常の Markdown ファイル群です。問題があれば早い段階で止められる順序で読みます。

```
openspec/changes/add-dark-mode/
├── proposal.md      1. the intent and scope   ← if this is wrong, stop here
├── specs/…/spec.md  2. the requirements       ← the heart of the review
├── design.md        (only for bigger changes) — the technical approach
└── tasks.md         3. the plan of work
```

すべての行を読む必要はありません。ファイルごとに 1 つずつ、計 3 つの質問に答える必要があります。

## 提案: これは正しい問題ですか?

まず `proposal.md` を開きます。「なぜ」と「何を」、つまり意図、範囲、アプローチを 1〜2 段落で確認します。

**良い提案:** 明確な意図が 1 つあり、範囲があなたの認識と一致し、なぜ今やる価値があるかが分かる。

**危険信号:**

- あなたが依頼した問題とは少し *違う* 問題を解決している。
- 範囲が拡大しました。あなたはテーマの切り替えを要求しましたが、提案では「その間に」認証にも触れています。
- 曖昧である。「設定ページを改善する」は範囲ではありません。「OS 設定を尊重するダークモードトグルを追加する」なら範囲です。

**答えるべき質問:** *これは自分が実際に求めたことと一致しているか？余計なものが入り込んでいないか？* 答えが「いいえ」なら、そこで止めます。先へ進まず、提案を修正してください（[差し戻しは安い](#pushing-back-is-cheap) を参照）。

## 仕様デルタ: 「完了」は正しく定義されていますか?

これがレビューの核心です。 `specs/` の下の仕様差分には、変更が出荷されたときに何が *真実*になるかが、要件とそれを証明するシナリオとして記載されています。

```markdown
## ADDED Requirements

### Requirement: Dark Mode Toggle
The system SHALL let a user switch between light and dark themes.

#### Scenario: Respects the OS preference on first load
- GIVEN a user who has never set a theme
- WHEN they open the app on a device set to dark mode
- THEN the app renders in dark mode
```

**良い要件:** テスターに渡せる明確な `SHALL`/`MUST` 文が 1 つあり、その文を実際に検証する GIVEN/WHEN/THEN シナリオが少なくとも 1 つある。

**危険信号:**

- **曖昧な要件。** 「システムは高速でなければなりません」を構築したりテストしたりすることはできません。何が速いの？
- **シナリオのない要件**、またはその要件をテストしないシナリオ。
- **最も価値がある発見: 欠けているもの。** AI は、あなたが *言ったこと* を忠実に書きます。あなたの仕事は、言い忘れたことに気づくことです。OS 設定を優先するケースが重要なのに、シナリオで触れられていなければ、このレビューには価値があります。

デルタを読んで、*システムがまさにこれだけを実行できたら嬉しいでしょうか?* ここにはまだコードに関するものは何もないので、変更するのは安価です。

## タスク: 作業計画は妥当ですか?

最後に`tasks.md`を開きます。これは、AI が実行する実装チェックリストです。

**良いタスク:** 順序立ったステップであり、各ステップが要件に対応していて、根拠の分からない作業がない。

**危険信号:**

- 対応する要件がないタスク（それはどこから来たのか）。
- 1 つの巨大な「機能を実装する」タスクで、実際の判断がすべて隠れている。
- 先ほど承認した範囲外のものに触れるタスク。

ここでやるのは見積もりや細かな管理ではありません。計画が、すでに受け入れた要件と一致しているかを確認します。

## 押し返すのは安い

3 つの質問のどれかで違和感があれば、そこで止めてください。フェーズはなく、何もロックされていません。問題を直してから進みます。[変更の編集](editing-changes.md) と同じく、方法は 2 つです。

- **ファイルを自分で編集します。** 変更提案は通常の Markdown です。スコープの説明を直し、要件を具体化し、不要なタスクを削除できます。
- **何が問題なのかを AI に伝え**、修正させます。 *「認証の変更を範囲外に削除します。」* *「ユーザーが既にテーマを選択している場合のシナリオを追加します。」* *「タスク 3 をスキーマと UI に分割します。」*

次に、変更した部分をもう一度読みます。あなたが署名する計画になるまで草案を書き直します。このやり取りが「機能」しているのです。

## コードの後: 確認してください

実装ができたら、`/opsx:verify` が 2 回目のレビューになります。アーティファクトとコードを読み直し、次の 3 つの観点で不一致を報告します。

| 観点 | チェック内容 |
| --- | --- |
| **完全性** | すべてのタスクが完了し、すべての要件が実装され、シナリオがカバーされているか |
| **正確さ** | 実装が仕様の意図と一致し、エッジケースが処理されているか |
| **一貫性** | 設計上の判断が実際にコードへ反映されているか |

```
You: /opsx:verify

AI:  Verifying add-dark-mode...

     COMPLETENESS
     ✓ All 8 tasks in tasks.md are checked
     ✓ All requirements in specs have corresponding code
     ⚠ Scenario "Respects the OS preference on first load" has no test coverage
```

問題は重大、警告、提案として示されますが、アーカイブは**ブロックされません**。差分を見える化し、判断はあなたに残します。これは「AI がコードを書いたか」と「合意したものを作ったか」の違いを確認するための手順です。

`/opsx:verify` は拡張されたプロファイルにあります。お持ちでない場合は、`openspec config profile` (その後 `openspec update`) でオンにするか、変更と差分を自分で再読み込みしてください。

## レビューのサイズを適切に調整する

すべての変更に完全なレビュー手順が必要なわけではありません。1 ファイルのタイプミス修正なら 20 秒の確認で十分です。認証、支払い、復旧できないデータに関わる変更なら、上記の質問をすべて確認してください。重要なのは形式ではなく、ミスが高くつく場所に注意を払い、そうでない場所では軽く済ませることです。

## 2 分間のチェックリスト

- [ ] 提案の意図は私が求めたことと一致します。
- [ ] スコープには余分なものは何も入り込んでいません。
- [ ] すべての要件はテストするのに十分なほど具体的です。
- [ ] すべての要件には、それを実際に実行するシナリオがあります。
- [ ] 私が最も気になるケースがカバーされています。
- [ ] タスクは要件にマップされます。神秘的なものや範囲外のものは何もありません。
- [ ] AI がまさにこれだけを構築し、それ以上のものを構築しなければ、私は安心します。

7 つすべてが合格した場合は、自信を持って `/opsx:apply` を実行してください。たとえ失敗しても、それは挫折ではありません。2 分間がその役割を果たしているのです。
