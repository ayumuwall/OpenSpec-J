# トラブルシューティング

具体的な問題に対する具体的な修正。各エントリは症状に名前を付け、考えられる原因を文で説明し、解決策を提供します。ここで問題が見つからない場合は、[FAQ](faq.md)] が役立つかもしれません。[Discord](https://discord.gg/YctCnvvshC)] も間違いなく役立ちます。

## インストールとセットアップ

### `openspec: command not found`

CLI がインストールされていないか、シェルが CLI を見つけられません。グローバルにインストールして以下を確認します。

```bash
npm install -g @ayumuwall/openspec@latest
openspec --version
```

インストールしても見つからない場合は、グローバル npm bin ディレクトリが `PATH` にない可能性があります。 `npm bin -g` を実行してグローバル バイナリが存在する場所を確認し、そのパスがシェル プロファイルに存在することを確認します。

### 「Node.js 20.19.0 以降が必要」

OpenSpec はノード 20.19.0 以降で実行されます。バージョンを確認し、必要に応じてアップグレードします。

```bash
node --version
```

bun を使用して OpenSpec をインストールする場合、OpenSpec はノード上で引き続き「実行」されるため、`PATH` 上で利用可能なノード 20.19.0 以降が必要であることに注意してください。 「インストール](installation.md)」を参照してください。

### `openspec init` が AI ツールを構成しませんでした

Init はどのツールをセットアップするかを尋ねます。ツールをスキップした場合、または別のツールを追加したい場合は、ツールを再度実行するか、非対話型フォームを使用します。

```bash
openspec init --tools claude,cursor
```

ツール ID の完全なリストは [サポートされているツール](supported-tools.md)] にあります。すべてに `--tools all` を使用し、ツールのセットアップをスキップするには `--tools none` を使用します。

## コマンドが表示されない

`/opsx:propose` (または同等のツール) が表示されない場合、または何も実行しない場合は、このリストを調べてください。チェックが早い順に並べられます。

1. **間違った場所にいる可能性があります。** スラッシュ コマンドは、端末ではなく AI アシスタントのチャットに入力されます。シェルに `/opsx:propose` と入力した場合、それが問題です。 [コマンドの仕組み](how-commands-work.md)]を参照してください。

2. **ファイルを再生成します。** プロジェクト ルートから:

「」バッシュ
オープン仕様のアップデート
「」

これにより、設定したすべてのツールのスキル ファイルとコマンド ファイルが書き換えられます。

3. **アシスタントを再起動します。** ほとんどのツールは起動時にスキルとコマンドをスキャンします。新しいウィンドウがそれを行うことがよくあります。

4. **ファイルが存在することを確認します。** クロード コードの場合、`.claude/skills/` に `openspec-*` フォルダーが含まれていることを確認します。他のツールは独自のディレクトリを使用しており、すべて [サポートされているツール](supported-tools.md)] にリストされています。

5. **このプロジェクトが初期化されていることを確認してください。** スキルはプロジェクトごとに書き込まれます。リポジトリのクローンを作成した場合、またはフォルダーを切り替えた場合は、そこで `openspec init` (または `openspec update`) を実行します。

6. **お使いのツールがコマンド ファイルをサポートしていることを確認してください。** いくつかのツール (Kimi CLI、ForgeCode、Mistral Vibe) は、生成された `opsx-*` コマンド ファイルを取得しません。代わりにスキルベースの呼び出しを使用します。形式はツールごとに異なります。「サポートされているツール](supported-tools.md)」および「コマンドの仕組み](how-commands-work.md#slash-command-syntax-by-tool)」を参照してください。

## 変更の処理

### 「変更が見つかりません」

コマンドは、どの変更を意味するのかを判断できませんでした。明示的に名前を付けるか、存在するものを確認します。

```bash
openspec list                    # see active changes
/opsx:apply add-dark-mode        # name the change in chat
```

また、正しいプロジェクト ディレクトリにいることも確認してください。

### 「アーティファクトの準備ができていません」

すべてのアーティファクトは、すでに作成されているか、依存関係を待ってブロックされています。何がブロックしているのかを確認してください。

```bash
openspec status --change <name>
```

次に、不足している依存関係を最初に作成します。順序を覚えておいてください。提案によって仕様と設計が可能になります。仕様とデザインを組み合わせることでタスクが可能になります。

### `openspec validate` が警告またはエラーを報告します

検証では、構造上の問題がないか仕様と変更をチェックします。メッセージを読みます。ファイルと問題の名前が示されています。

```bash
openspec validate <name>           # validate one item
openspec validate --all            # validate everything
openspec validate --all --strict   # stricter checks, good for CI
```

一般的な原因は、必須セクションの欠落 (シナリオのない仕様など) または不正なデルタ ヘッダーです。ファイルを修正して再実行してください。 [CLI リファレンス ](cli.md#openspec-validate) には出力形式が記載されています。

### AI が不完全または間違ったアーティファクトを作成した

AI には十分なコンテキストがありませんでした。いくつかのレバーが役に立ちます。

- `openspec/config.yaml` にプロジェクト コンテキストを追加して、スタックと規約がすべてのリクエストに挿入されるようにします。 「カスタマイズ](customization.md#project-configuration)」を参照してください。
- たとえば仕様にのみ適用されるガイダンスとして、アーティファクトごとに `rules:` を追加します。
- 提案するときは、より詳細な説明を入力してください。
- `/opsx:continue` ですべてを一度に実行するのではなく、拡張された `/opsx:ff` を使用して、一度に 1 つのアーティファクトを作成し、それぞれを確認します。

### アーカイブが完了しない、または未完了のタスクについて警告が表示される

アーカイブは未完了のタスクを *ブロック*しませんが、アーカイブは通常、作業が完了したことを意味するため、警告が表示されます。タスクが意図的に残っている場合 (部分的な変更を提出している場合)、続行します。それ以外の場合は、最初にタスクを完了してください。まだ同期していない場合、アーカイブは仕様差分をメイン仕様に同期することも提案します。断る理由がない限り、「はい」と言ってください。

## 構成

### 私の `config.yaml` は適用されません

いつもの容疑者は3名：

1. **ファイル名が間違っています。** `openspec/config.yaml` ではなく、`.yml` である必要があります。
2. **無効な YAML。** 任意の YAML バリデーターを介して実行します。 CLI は、構文エラーも行番号とともに報告します。
3. **再起動が必要でした。** 再起動は必要ありません。構成の変更はすぐに有効になります。

### "ルール内の不明なアーティファクト ID: X"

`rules:` の下のキーは、スキーマ内のどのアーティファクトとも一致しません。デフォルトの `spec-driven` スキーマの場合、有効な ID は `proposal`、`specs`、`design`、`tasks` です。スキーマの ID を確認するには:

```bash
openspec schemas --json
```

### 「コンテキストが大きすぎます」

`context:` フィールドはすべてのリクエストに挿入されるため、意図的に 50 KB に制限されています。要約するか、貼り付ける代わりに長いドキュメントにリンクしてください。無駄のないコンテキストにより、より優れた、より高速な結果が得られます。

### 「スキーマが見つかりません」

参照したスキーマ名は存在しません。利用可能なものをリストし、スペルを確認します。

```bash
openspec schemas                    # list available schemas
openspec schema which <name>        # see where a schema resolves from
openspec schema init <name>         # create a custom one
```

「カスタマイズ](customization.md#custom-schemas)」を参照してください。

## 従来のワークフローからの移行

### 「非対話モードでレガシー ファイルが検出されました」

CI または非対話型シェルを使用しており、OpenSpec はクリーンアップすべき古いファイルを見つけましたが、プロンプトを表示できません。自動的に承認します:

```bash
openspec init --force
```

### 移行後にコマンドが表示されない

IDE を再起動します。スキルは起動時に検出されます。それでも表示されない場合は、`openspec update` を実行し、[サポートされているツール](supported-tools.md)] でファイルの場所を確認してください。

### 古い `project.md` は移行されませんでした

それは意図的です。 OpenSpec は、`project.md` を自動的に削除することはありません。これは、作成したコンテキストが保持されている可能性があるためです。有用な部分を `config.yaml` の `context:` セクションに移動してから、自分で削除してください。 [移行ガイド](migration-guide.md#migrating-projectmd-to-configyaml)] では、抽出を行うために AI に渡すプロンプトも含めて、これについて説明します。
