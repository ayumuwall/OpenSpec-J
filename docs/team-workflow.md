# チームの OpenSpec

他のガイドに記載されている内容は、ソロでも 20 人のチームでも同じように機能します。チームにどのような変更があるかというと、仕様はどこにあるのか、チームメイトは計画をどのようにレビューしているのか、そしてこれらはすでにあるプルリクエストのフローにどのように適合するのかなど、境界線に近い疑問が生じます。

短く言うと、変更はただのファイルであり、OpenSpec は Git を操作しません。そのため、既存のワークフローを置き換えるのではなく、その中に自然に収まります。このページでは、うまく運用するための規則を説明します。

## 1 つのルール: OpenSpec は Git に触れない

OpenSpec は `openspec/` 配下の通常の Markdown を読み書きします。プロジェクトをコミット、ブランチ作成、プッシュ、プルすることはありません。また、[store](stores-beta/user-guide.md) を勝手に複製したり同期したりすることもありません。つまり:

- **他のソースと同じように `openspec/` をコミットします。** 仕様、アクティブな変更、アーカイブはプロジェクト履歴の一部です。フォルダー全体をコミットしてください。詳しくは [FAQ](faq.md#should-i-commit-the-openspec-folder-to-git) を参照してください。
- **変更は、コードのようにバージョン管理するフォルダーです。** `openspec/changes/add-dark-mode/` はブランチ上の単なるファイルです。
- **以下の内容はすべて慣例であり、強制ではありません。** OpenSpec ではこのようにすることはできません。ちょうどきれいにフィットします。

## 日常のループ

適切に機能するワークフローは、変更をブランチとプルリクエストに対応させます。

```
git switch -c add-dark-mode        start a branch, as usual
   │
/opsx:propose add-dark-mode        draft the plan (proposal + specs + tasks)
   │
REVIEW THE PLAN                    you read it before any code — see Reviewing a Change
   │
/opsx:apply                        build it; artifacts + code change together
   │
git commit && open a PR            the PR contains the spec delta AND the code
   │
teammate reviews, merges
   │
/opsx:archive                      fold the delta into specs/, move the change to archive/
```

計画とコードは同じブランチ内に並行して存在するため、チームメイトは両方を一緒にレビューします。6 か月後もアーカイブされた仕様には、コードがそのようになる理由が説明されています。

## プルリクエストで仕様を確認する

ここでチームは成果を実感します。 PR に変更の差分仕様が含まれている場合、レビュー担当者は、コードを 1 行も読む前に、生の差分では決して得られないもの、つまり **この変更が何を行うべきかについての平易な言葉** を得ることができます。

レビュー担当者にとって適切なレビュー順序:

1. **`proposal.md` を読んでください** — これは適切な問題と範囲ですか?
2. **`specs/` 配下の差分を読みます** - 「完了」の定義は正しいですか？これは PR 上で行う [変更レビュー](reviewing-changes.md) の短時間チェックです。
3. **次に、コードの差分を読んでください** — それはまさにその要件を満たしていますか?

*アプローチ*に同意しないレビュー担当者は、コードを 300 行にわたって再議論する代わりに、低コストで提案に反対することができます。仕様差分を PR 説明の先頭近くに置くか、レビュー担当者に変更フォルダーを指示して、そこから開始できるようにします。

## アーカイブする場合

アーカイブすると、変更の差分がメインの `openspec/specs/` に折りたたまれ、変更フォルダーが `openspec/changes/archive/YYYY-MM-DD-<name>/` に移動します。 `specs/` は **真実の共有情報源**であるため、チームにとってタイミングは重要です。実行可能な 2 つの規則:

- **PR マージ後にアーカイブします (推奨)。** ブランチにはアクティブな変更が含まれます。メイン ブランチにマージされたら、そこにアーカイブします (多くの場合、小規模なフォローアップ コミットまたはスケジュールされたクリーンアップ)。これにより、共有 `specs/` は実際に出荷された作業のみで前進し続けます。
- **PR 内にアーカイブします。** 小規模チームにとっては簡単です。コードを追加した同じ PR も同期され、アーカイブされます。トレードオフとして、`specs/` の差分とコードの差分が一緒に着地するため、PR のノイズが大きくなる可能性があります。

1 つを選択し、一貫性を保ってください。いずれにせよ、`/opsx:archive` はタスクが完了していることを確認し、最初に同期することを提案するため、誤って中途半端にマージされることはありません。

## 二人、並行変更

変更は個別のフォルダーであるため、衝突しません。

- **変更が違えば、人が変わっても問題ありません。** `add-dark-mode` と `rate-limit-login` は、異なるブランチの異なるフォルダーです。両方がアーカイブされるまで、お互いに触れることはありません。
- **1 つの変更、1 人の所有者。** 2 人が同じ変更フォルダーを編集すると、2 人が同じファイルを編集する場合と同じように競合します。変更は 1 人が担当するか、2 つの変更に分割してください（[変更を適切な大きさに保つ](writing-specs.md#right-size-the-change) もう 1 つの理由です）。
- **競合が起きる場所は `specs/` です。** 2 つの変更が *同じ* 要件を変更している場合、後からアーカイブする変更は `openspec/specs/…/spec.md` で競合します。通常のマージ競合と同じように、実際に採用する動作を表す要件だけを残して解決してください。これは頻繁に起きるものではなく、むしろ意図した挙動です。システムの振る舞いについて 2 つの変更が食い違っていることを Git が知らせてくれます。

## 計画が 1 つのリポジトリを超えた場合

ここまでの説明は、計画がコードリポジトリ内の `openspec/` フォルダーにある前提です。これが通常のデフォルトです。計画が複数のリポジトリやチームにまたがる場合（1 つの機能が 3 つのサービスに影響する、あるチームが所有する要件を別チームが使う、など）は、ベータ版の **ストア** 機能を使います。計画を独立したリポジトリに置き、各コードリポジトリから参照できます。まずは [ストアユーザーガイド](stores-beta/user-guide.md) を参照してください。
