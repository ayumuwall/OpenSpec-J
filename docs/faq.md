# よくある質問

よく寄せられる質問に短く答えます。実際には「何かが壊れている」という相談であれば、[トラブルシューティング](troubleshooting.md) の方が適切です。用語の定義は [用語解説](glossary.md) を参照してください。

## 基本

### OpenSpec を一言で言うと何ですか?

コードを作成する前に、ユーザーと AI コーディング アシスタントが何を構築するか書面で合意するための軽量レイヤーです。

### なぜそれが必要なのでしょうか?

AI アシスタントは、間違っていても自信を持って実装しがちだからです。要件がチャット履歴の中にしかないと、AI は足りない部分を推測で埋めます。OpenSpec は、修正コストが安い早い段階で合意を作ります。詳しくは [コアコンセプトの概要](overview.md) を参照してください。

### すべてに使用する必要がありますか?

いいえ。合意が重要な作業に使ってください。1 文字のタイプミス修正なら、この手順は割に合わないかもしれません。それで構いません。

### 既存の大規模なコードベースで使用できますか、それとも新しいプロジェクトのみで使用できますか?

既存のコードベースこそ主な対象です。OpenSpec はブラウンフィールドを前提にしています。アプリ全体を事前に文書化する必要はありません。仕様は各変更が影響する範囲だけを書き、実際の作業に合わせて少しずつ育てます。詳しくは [既存プロジェクトで OpenSpec を使う](existing-projects.md) を参照してください。

### それは 1 つの AI ツールに関連付けられていますか?

いいえ。OpenSpecはClaude Code、Cursor、Devin Desktop、GitHub Copilot、Gemini CLI、Codexなど、30以上のアシスタントと連携します。完全な一覧とツールごとの詳細は、[サポートされているツール](supported-tools.md)を参照してください。

## コマンドの実行

### `/opsx:propose` はどこに入力すればよいですか?

端末ではなく、AI アシスタントのチャットで。これは最も一般的な混乱点であるため、独自のページがあります: [コマンドの仕組み](how-commands-work.md)。短いバージョン: `openspec ...` はターミナルで実行され、`/opsx:...` はチャットで実行されます。

### 「対話モードを開始」するにはどうすればよいですか?

開始用の特別なモードはありません。普段どおり AI アシスタントを開き、チャットにスラッシュコマンドを入力します。スラッシュコマンドが OpenSpec の入口です。ターミナルで対話的に使う機能としては、仕様と変更を閲覧するダッシュボード `openspec view` があります。詳しくは [コマンドの仕組み](how-commands-work.md) を参照してください。

### スラッシュコマンドを入力しましたが、何も起こりませんでした。なぜ？

AIチャットではなくターミナルへ入力した、ツールが認識しない表記を使った、またはコマンドが未インストールの可能性があります。ファイルがない、あるいはツールを未設定の場合は `openspec init` を実行してください。`openspec update` は既存ファイルだけを更新します。その後アシスタントを再起動し、「Getting started」に表示された形式を使ってください。詳しくは[呼び出し方法](supported-tools.md#how-to-invoke)と[トラブルシューティング](troubleshooting.md#commands-dont-show-up)を参照してください。

### あるツールでは構文 `/opsx:propose` が使用され、別のツールでは `/opsx-propose` が使用されるのはなぜですか?

AIツールごとにカスタムコマンドの表示形式が異なり、OpenSpecは生成先に合う表記を使います。`opsx-propose.md` というコマンドファイルは `/opsx-propose`、`commands/opsx/` 配下のファイルは `/opsx:propose` と入力します。コマンドではなくスキルを使うツールではスキル名を使い、Codexは `$openspec-propose`、Kimi Codeは `/skill:openspec-propose` です。`openspec init` の「Getting started」には選択したツール向けの形式が表示されます。完全な表は[呼び出し方法](supported-tools.md#how-to-invoke)を参照してください。

### スキルとコマンドの違いは何ですか?

どちらも、アシスタントがワークフローを実行できるように OpenSpec が書き込むファイルです。スキル（`.../skills/openspec-*/SKILL.md`）は新しいクロスツール向けの形式です。コマンドファイル（`.../commands/opsx-*`）は従来のツール別スラッシュコマンドです。利用者が選ぶ必要はありません。スラッシュコマンドを入力すれば、そのツールに必要な形式が使われます。

## ワークフロー

### 何を構築すればよいかわからない場合は、どこから始めればよいですか?

`/opsx:explore` から始めます。これは、変更やコードを作る前にコードベースを読み、選択肢を整理し、曖昧な問題を具体的な計画に変えるための思考パートナーです。デフォルトプロファイルに含まれているため、いつでも使えます。計画が明確になったら `/opsx:propose` に引き継ぎます。AI が自信を持って違うものを作ってしまうのを防ぐ、最も有効な習慣です。詳しくは [まずは探索する](explore.md) を参照してください。

### 最も単純なフローは何ですか?

```text
/opsx:explore (optional)   then   /opsx:propose <what you want>   then   /opsx:apply   then   /opsx:archive
```

探索で考え、提案で計画を下書きし、apply で実装し、archive で仕様へ反映して保管します。必要なものがすでに明確なら、探索は省略して構いません。

### `/opsx:propose` と `/opsx:new` の違いは何ですか?

`/opsx:propose` はデフォルトのワンステップコマンドです。変更を作成し、計画成果物をまとめて作ります。`/opsx:new` は拡張コマンドセットの一部で、空の変更だけを作成します。その後 `/opsx:continue` で 1 つずつ、または `/opsx:ff` でまとめてアーティファクトを作成できます。段階的な制御が不要なら `propose` を使ってください。詳しくは [コマンド](commands.md) を参照してください。

### `core` および拡張プロファイルとは何ですか?

プロファイルは、どのスラッシュコマンドをインストールするかを決めます。**core**（デフォルト）では `propose`、`explore`、`apply`、`update`、`sync`、`archive` が使えます。**expanded** セットでは、より細かく制御するために `new`、`continue`、`ff`、`verify`、`bulk-archive`、`onboard` が追加されます。`openspec config profile` で切り替え、`openspec update` で適用します。

### `/opsx:sync` を実行する必要がありますか?

通常は不要です。Sync は変更の仕様差分をメイン仕様へマージしますが、`/opsx:archive` でも通常その処理を提案します。長期の変更など、アーカイブ前に仕様だけ先にマージしたい場合にのみ手動で実行します。詳しくは [コマンド](commands.md#opsxsync) を参照してください。

### 提案、仕様、またはタスクを開始した後に編集するにはどうすればよいですか?

ファイルを編集するだけです。`openspec/changes/<name>/` のアーティファクトはすべて通常の Markdown で、ロックされたフェーズや特別な編集モードはありません。手で直しても、AI に「キューを使う設計に更新して」のように頼んでも構いません。AI は常に現在のファイル内容を前提に動きます。詳しくは [変更の編集と反復](editing-changes.md) を参照してください。

### 計画の一部を実行した後で、戻って計画を変更できますか?

はい、いつでも戻れます。ワークフローは流動的で、レビューや編集がロックされるフェーズはありません。アーティファクトを編集してから続行してください。コードが計画と一致しているか構造的に確認したい場合は、`/opsx:verify` を実行します。詳しくは [変更の編集と反復](editing-changes.md#how-do-i-go-back-to-review-after-implementing) を参照してください。

### コードを手動で編集しました。仕様とどうやって調和させればいいのでしょうか？

アーカイブすると仕様が記録上の真実になるため、アーカイブ前にずれを解消してください。コードが正しいなら、出荷した動作に合わせて仕様差分を更新します。仕様が正しいなら、コードが一致するまで実装を続けます。`/opsx:verify` は不一致を見つけるのに役立ちます。詳しくは [変更の編集と反復](editing-changes.md#i-edited-the-code-by-hand-how-do-i-reconcile-that-with-openspec) を参照してください。

### 既存の変更を更新するのではなく、新しい変更を開始するのはどのような場合ですか?

同じ作業を磨き込んでいるだけなら更新します。意図が根本的に変わったり、スコープが別作業と言えるほど広がったりした場合は、新しい変更として始め直します。判断の目安と例は [ワークフロー](workflows.md#when-to-update-vs-start-fresh) にあります。

### セッションがコンテキストから外れてしまった場合、または実装中に要件が変更された場合はどうなりますか?

ここで仕様が効きます。計画はチャット履歴だけでなくファイルに保存されているため、コンテキストをクリアして新しい AI セッションを始め、`/opsx:apply` から再開できます。AI はアーティファクトを読み、最初の未完了タスクから進めます。要件が変わった場合は、新しい現実に合わせてアーティファクトを編集して続行してください。実装前にコンテキストウィンドウを整理しておくと、結果が安定します。

<a id="should-i-commit-the-openspec-folder-to-git"></a>

### `openspec/` フォルダーを git にコミットする必要がありますか?

はい。仕様、アクティブな変更、アーカイブはプロジェクト履歴の一部です。他のソースと同様にそれらをコミットします。特にアーカイブは、システムがなぜそのように動作するのかを示す永続的な記録になります。

## 仕様と変更点

### 仕様と設計には何が含まれますか?

仕様には、システムの観察可能な動作、入力、出力、エラー条件などを書きます。設計には、技術的なアプローチ、アーキテクチャ上の判断、変更するファイルなど、どう作るかを書きます。外部から見える動作を変えずに実装だけ変えられるなら、それは仕様ではなく設計に属します。詳しくは [コンセプト](concepts.md#what-a-spec-is-and-is-not) を参照してください。

### 仕様差分とは何ですか?

仕様全体を再説明するのではなく、`ADDED`、`MODIFIED`、`REMOVED` セクションで変更点だけを説明する仕様です。OpenSpec はこの形式により、既存システムへの変更を扱いやすくします。詳しくは [コンセプト](concepts.md#delta-specs) を参照してください。

### アーカイブされた変更はどこに行くのですか?

すべてのアーティファクトを保持したまま、`openspec/changes/archive/YYYY-MM-DD-<name>/` に移動します。何も削除されません。アクティブな変更一覧から外れるだけです。

## 構成とカスタマイズ

### 技術スタックについて AI に伝えるにはどうすればよいですか?

`openspec/config.yaml` の `context:` に書きます。この内容はすべての計画リクエストに挿入されるため、AI は常にスタックや規約を前提にできます。詳しくは [カスタマイズ](customization.md#project-configuration) を参照してください。

### 英語以外の言語で仕様を生成できますか?

はい。設定の `context:` に言語指定を追加します。[多言語](multi-language.md) には、複数の言語向けのコピー＆ペースト可能な例があります。

### ワークフロー自体を変更できますか?

はい。カスタムスキーマを使います。スキーマは、どのアーティファクトを作るか、それらがどう依存するかを定義します。まず `openspec schema fork spec-driven my-workflow` でデフォルトを複製し、必要に応じて編集してください。詳しくは [カスタマイズ](customization.md#custom-schemas) を参照してください。

## モデル、プライバシー、アップグレード

### どの AI モデルを使用すればよいですか?

OpenSpec は高度な推論モデルで最もよく機能します。 README では、計画と実装の両方に Codex 5.5 や Opus 4.7 などのモデルを推奨しています。また、コンテキスト ウィンドウをクリーンな状態に保ちます。最良の結果を得るには、実装前にコンテキスト ウィンドウをクリアしてください。

### OpenSpec はデータを収集しますか?

匿名の使用状況統計 (コマンド名とバージョンのみ) を収集します。引数、パス、コンテンツ、個人データはなく、CI では自動的にオフになります。 `export OPENSPEC_TELEMETRY=0` または `export DO_NOT_TRACK=1` でオプトアウトします。

### アップグレードするにはどうすればよいですか?

2 つのステップ。パッケージ (`npm install -g @ayumuwall/openspec@latest`) をアップグレードし、各プロジェクト内で `openspec update` を実行して、生成されたスキルとコマンドを更新します。

### OpenSpec をアンインストールするにはどうすればよいですか?

これはグローバル パッケージとプロジェクト内のファイルだけであるため、アンインストール コマンドはありません。パッケージ (`npm uninstall -g @ayumuwall/openspec`) を削除し、必要に応じて `openspec/` ディレクトリと生成されたツール ファイルを削除します。安全に保存できるものを含め、ステップバイステップは [インストール: ](installation.md#uninstalling) のアンインストール] に記載されています。
