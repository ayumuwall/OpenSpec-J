# 変更の編集と反復

**変更内のすべての成果物は、いつでも編集できる通常の Markdown ファイルです。** ロックされた「計画フェーズ」、承認ゲート、特別な編集モードはありません。実装開始後に提案を変えたくなったら、`proposal.md` を開いて直します。実装中に設計の誤りに気づいたら、`design.md` を修正して続けます。それが基本であり、意図した使い方です。

このページは、「ちょっと待って、戻って変更してもいいですか?」と思ったときのためのページです。はい。一般的なケースごとにその方法を示します。

## 何かを編集するための 2 つの方法

常に 2 つの方法があります。

1. **ファイルを直接編集します。** アーティファクトは `openspec/changes/<name>/` にある通常の Markdown ファイルです。エディターで `proposal.md`、`design.md`、`tasks.md`、または `specs/` 配下の仕様差分を開いて変更します。それ以外の特別な操作は不要です。

2. **AI に改訂を依頼します。** チャットで、「提案を更新してキャッシュ案を削除し、レート制限のセクションを追加して」、または「設計ではポーリングではなくキューを使う必要がある」など、希望を伝えてください。AI は変更内の残りの内容をコンテキストとして使い、アーティファクトを編集します。

状況に合う方法を選んでください。ちょっとした言い回しの修正ならファイルを直接編集します。方針を考え直す必要があるなら、AI に全体のコンテキストを踏まえて修正させます。

## 「開始後に提案書 (または仕様書) を更新するにはどうすればよいですか?」

そのまま更新します。同じ変更を磨き込むだけです。

拡張コマンドを使っている場合は、アーティファクトを編集してから `/opsx:continue` で新しい状態から続きを作るか、`/opsx:apply` で更新後の計画に沿って実装を続けます。デフォルトの `core` コマンドを使っている場合は、アーティファクトを編集して `/opsx:apply` を実行します。現在のファイルを読み取るため、更新後の内容に基づいて実装されます。

考え方は単純です。成果物は実際の計画ですが、署名済みで変更不能な契約ではありません。AI は常に現在の内容に基づいて動くため、内容を編集すれば作業を制御できます。

```text
You: I want to change the approach in this change.

You: [edit design.md, or tell the AI:]
     Update design.md to use a background job instead of a synchronous call.

AI:  Updated design.md. The task list still fits; want me to continue applying?

You: /opsx:apply
```

これが、よくある質問への答えです。「プロポーザルを更新する」専用コマンドは不要なので、別コマンドはありません。ファイルが情報源であり、それを手動または AI 経由で編集することが更新です。

## 「実装後にレビューに戻るにはどうすればよいですか?」

そもそも離れていないので、「戻る」必要はありません。ワークフローは流動的です。レビュー、編集、実装は、閉じたフェーズの列ではありません。

具体的には、`/opsx:apply` の作業を行った後、次のようになります。

- 計画を見直したい場合は、アーティファクトを開いて読むか、ターミナルで `openspec show <change>` を実行して統合ビューを表示します。
- 変更すべき点が見つかった場合は、アーティファクトを編集するか、AI に編集を依頼してから続けます。
- コードが計画と一致しているか構造的に確認したい場合は、`/opsx:verify`（拡張コマンド）を実行します。処理はブロックせず、完全性、正確性、一貫性をレポートします。詳しくは [ワークフロー: Verify](workflows.md#verify-check-your-work) を参照してください。

レビューは実装後を含めていつでもできます。戻るべき「レビューフェーズ」はありません。

<a id="i-edited-the-code-by-hand-how-do-i-reconcile-that-with-openspec"></a>

## 「コードを手動で編集しました。それを OpenSpec と調和させるにはどうすればよいですか?」

これはよく起きますが、問題ありません。エディターで何かを調整した結果、コードとアーティファクトがずれることがあります。どちらが正しいかを決め、もう一方を合わせます。

- **コードは正しくなりましたが、仕様は古いです。** 実際に出荷した動作を説明するために仕様差分 (および関連する場合はタスク) を更新します。アーカイブすると仕様が信頼できる情報源にマージされるため、仕様はアーカイブする前に現実と一致する必要があります。
- **仕様は正しいですが、コードがずれています。** コードが仕様と一致するまでビルドまたは修正を続けます。

不一致を素早く見つけるには `/opsx:verify` を使います。アーティファクトとコードを読み取り、どこがずれているかを示します。その出力を修正用の ToDo リストとして扱い、内容が揃ったらアーカイブします。

原則として、アーカイブ後は仕様が記録上の真実になります。そのため、アーカイブ前に、コードが実際に何をするかを仕様へ正確に反映してください。手動編集は歓迎です。ただし、仕様とコードを黙ってずれたままにしないでください。

## 満足できない提案を修正する

生成された提案が的を外した場合、次の 3 つの良い方法があります。

- **その場で反復します。** AI に何が違うか（「範囲が広すぎるので、管理機能は削除してください」など）を伝え、修正させます。最も低コストで、通常はこれで十分です。
- **最初に検討してから、再提案します。** アイデア自体が不明瞭な場合は、`/opsx:explore` に戻って考え直し、そこからより鋭い提案を作ります。詳しくは [まずは探索する](explore.md) を参照してください。
- **最初からやり直します。** 意図が根本的に変わった場合、古い変更にパッチを適用するよりも、新しい変更の方が明確になることがあります。

この最後の動きには、次の独自の決定ガイドがあります。

## いつ更新するか、新しい変更を開始するか

短く言うと、**同じ作業を磨き込んでいるなら更新します。意図が根本的に変わった場合、または範囲が別の作業へ広がった場合は、新しく始めます。**

- 同じ目標で、より良いアプローチに変えるだけなら更新します。
- 範囲を狭める場合（MVP を今出し、詳細は後で対応するなど）は、更新してアーカイブし、フェーズ 2 を新しい変更として始めます。
- 問題自体が変わった場合（「ダークモードを追加する」が「完全なテーマシステムを構築する」になったなど）は、新しい変更にします。

完全なフローチャートと実例は [ワークフロー: 更新するか、新しく始めるか](workflows.md#when-to-update-vs-start-fresh) にあります。より詳しい説明は [OPSX: 更新するか、新しく始めるか](opsx.md#when-to-update-vs-start-fresh) を参照してください。

## タスクに関するメモ

`tasks.md` は、凍結された計画ではなく、生きたチェックリストです。実装するときに、発見したタスクを追加したり、不要であることが判明したタスクを削除したり、順序を変更したりできます。 AI は、`/opsx:apply` 中に完了すると項目にチェックを入れ、後で戻ってきた場合は、最初のチェックされていないタスクから再開します。リストは途中で編集されることが予想されます。
