# コアコンセプトの概要

**OpenSpec は、ユーザーと AI の間の軽量の合意レイヤーです。** あなたが変更の内容を書き留め、AI が詳細を草案し、両者が同じ計画を検討して、初めてコードが記述されます。このページは、メンタル モデル全体を 1 つの画面上に表示したものです。ロングバージョンが必要な場合は、[Concepts](concepts.md)] にあります。

アイデア全体を 5 つの単語でまとめます。**まず同意し、次に自信を持って構築します。**

## 5 つのアイデア

OpenSpec のすべては 5 つの概念に基づいて構築されています。これらを学び、残りは詳細です。

**1.仕様は真実です。** 仕様とは、システムが *現時点* でどのように動作するかを記述します。これは、ドメイン (`openspec/specs/`、`auth/`、`payments/`) ごとに編成された `ui/` に存在します。仕様は要件 (「システムは 30 分後にセッションを期限切れにするものとする」) とシナリオ (具体的な指定/いつ/その後の例) で構成されます。仕様とは、「このソフトウェアは何をするのか?」に対する合意された単一の答えであると考えてください。

**2.変更は 1 つの作業単位です。** 動作を追加、変更、または削除する場合は、変更を作成します。つまり、その作業に関するすべてを 1 か所に保持する `openspec/changes/` 内のフォルダーです。提案、設計、タスクリスト、仕様の編集。 1 つの変更、1 つのフォルダー、1 つの機能。

**3.仕様差分は、世界全体ではなく、何が変更されているかを説明します。** 変更の内部では、仕様全体を書き換えることはありません。小さなデルタを書きます。この要件は `ADDED`、これは `MODIFIED`、もう 1 つは `REMOVED` となります。これは、OpenSpec が未開発のシステムだけでなく、既存のシステムの編集を得意とする秘訣です。宛先ではなく、差分を説明します。

**4.アーティファクトは相互に構築されます。** 変更には、自然な順序で作成されたいくつかのドキュメントが含まれており、それぞれが次のドキュメントにフィードされます。

```text
proposal ──► specs ──► design ──► tasks ──► implement
   why        what       how       steps      do it
```

いつでもどれでも再訪できます。それらはゲートではなくイネーブラーです。 (詳しくは以下をご覧ください。)

**5.アーカイブすると、変更が真実に戻されます。** 作業が完了したら、変更をアーカイブします。その仕様差分はメイン仕様にマージされ、変更フォルダーは日付スタンプ付きで `changes/archive/` に移動します。これで、仕様が新しい現実を表し、次の変更に備える準備が整いました。サイクルは終了します。

## 全体像

```text
┌─────────────────────────────────────────────────────────────────┐
│                          openspec/                              │
│                                                                 │
│   ┌──────────────────┐         ┌──────────────────────────┐    │
│   │     specs/       │         │        changes/          │    │
│   │                  │ ◄─────  │                          │    │
│   │ source of truth  │  merge  │ one folder per change    │    │
│   │ how things work  │  on     │ proposal · design ·      │    │
│   │ today            │ archive │ tasks · delta specs      │    │
│   └──────────────────┘         └──────────────────────────┘    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

フォルダーが 2 つあります。 `specs/` が真実です。あなたが提案しているのは`changes/`です。アーカイブは提案を真実に導きます。

## 実際に実行するループ

デフォルトの設定では、1 日は次のようになります。必要に応じて、最初によく考えてください。次に、1 つのコマンドで計画の草案を作成し、それを読み、次のコマンドでそれを構築し、最後のコマンドでファイルに保存します。

```text
/opsx:explore                   →  (optional) think it through with the AI first
/opsx:propose add-dark-mode     →  AI drafts proposal, specs, design, tasks
        (you read and adjust the plan)
/opsx:apply                     →  AI builds it, checking off tasks
/opsx:archive                   →  specs updated, change archived
```

**疑問がある場合は、探索することから始めてください。** `/opsx:explore` は、リスクのない思考パートナーです。コードを読み取り、オプションをレイアウトし、成果物が存在する前に曖昧なアイデアを具体的な計画に変換します。これは、曖昧なプロンプトから「何か」を構築してしまう AI に対する最も効果的な防止策です。あなたが何を望んでいるのかはすでに正確にわかっていますか？ `/opsx:propose` まで直接スキップしてください。いずれにせよ、Explore はデフォルトプロファイルに含まれているため、いつでも利用できます。 [探索ガイド](explore.md)]を参照してください。

これらは、AI アシスタントのチャットに入力されるスラッシュ コマンドです。セットアップ (`openspec init`) は端末で行われます。この分割が初めての場合は、[コマンドの仕組み](how-commands-work.md)] を最初に読んでください。それが最も一般的な混乱のポイントです。

## 「ゲートではなくイネーブラー」

このフレーズは OpenSpec のあらゆる場所で使用されます。その意味を簡単に説明します。

旧来の仕様プロセスはウォーターフォールです。計画を終えると *その後*、実装が許可されますが、後戻りするのは苦痛です。 OpenSpec はそれを拒否します。 `proposal → specs → design → tasks` という順序は、次に何を「強制」されるかではなく、次に何が「可能」になるかを示しています。

導入中に設計が間違っていたことに気づきましたか? `design.md` を編集して続行します。範囲を縮小する必要があることを理解していますか?提案を更新します。何もロックされません。依存関係は、AI が必要なコンテキストを得るためにのみ存在します (ベースとなる仕様がなければ、優れたタスクを作成することはできません)。ユーザーを囲い込むためではありません。

ここでの強みは誠実さです。実際の作業は面倒で反復的なものですが、OpenSpec はそれを許容します。トレードオフは規律です。前進を強制するものは何もないので、変更を無秩序に広げるのではなく、変更に焦点を合わせ続けるのはあなたの責任です。 [Workflows](workflows.md) ガイドには、そのための良い習慣が記載されています。

## これがわずかなオーバーヘッドを伴う価値がある理由

明らかな真実: OpenSpec はステップを追加します。構築する前に短い計画を書きます。それで何が得られるのでしょうか？

- **損をする前に、間違った方向転換に気づきます。** 1 段落の提案書の誤解を修正するのは無料です。 AI が 400 行を書いた後でそれを修正することはできません。
- **計画とコードは同じリポジトリに残ります。** 6 か月後、システムがそのように動作する理由が仕様によって (および次の AI セッションで) わかります。
- **変更はレビュー可能です。** 変更フォルダーはきちんとしたパッケージです。提案を読み、差分をざっと読み、タスクを確認します。チャット履歴を掘り返す必要はありません。
- **既存のコードベースに適合します。** デルタは、最初に全体を文書化することなく、50,000 行のアプリへの変更を指定できることを意味します。

そして正直なトレードオフ: 本当に些細な 1 行の修正の場合、形式的な手順は報われないかもしれませんが、それは問題ありません。 OpenSpec は軽量になるように設計されていますが、無料ではありません。同意が重要な場合に使用してください。AI を使用すると、漠然と要求したものは何でも自信を持って構築してくれることがほとんどです。
