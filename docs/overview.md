# コアコンセプトの概要

**OpenSpec は、あなたと AI の間に置く軽量な合意レイヤーです。** まず変更内容を書き出し、AI が詳細を下書きし、同じ計画を確認してからコードを書きます。このページでは、全体のメンタルモデルを短くまとめます。詳しい説明は [コンセプト](concepts.md) を参照してください。

要点は 1 つです。**先に合意し、その後で自信を持って実装する。**

## 5 つの考え方

OpenSpec は、次の 5 つの概念を中心に動きます。ここを押さえれば、残りは細部です。

**1. 仕様がソース・オブ・トゥルースです。** 仕様は、システムが *現時点で* どう動くべきかを記述します。`openspec/specs/` 配下に、`auth/` や `payments/` のようなドメイン別に配置します。仕様は、要件（例:「システムは 30 分の無操作後にセッションを期限切れにしなければならない。(SHALL)」）と、それを具体的に確認するシナリオで構成されます。仕様は「このソフトウェアは何をするのか？」に対する、合意済みの答えです。

**2. 変更は 1 つの作業単位です。** 動作を追加・変更・削除するときは、`openspec/changes/` に変更フォルダーを作ります。そこに提案、設計、タスクリスト、仕様差分をまとめます。1 つの変更、1 つのフォルダー、1 つの目的です。

**3. 仕様差分は、世界全体ではなく「変わる部分」だけを説明します。** 変更の中で仕様全体を書き直す必要はありません。小さな差分を書きます。この要件は `ADDED`、この要件は `MODIFIED`、別の要件は `REMOVED`、という形です。これにより、OpenSpec は新規開発だけでなく、既存システムの変更にも向きます。完成形を丸ごと書くのではなく、差分を説明します。

**4. アーティファクトは順番に文脈を積み上げます。** 変更には、自然な順序で作る複数のドキュメントがあります。それぞれが次のドキュメントの材料になります。

```text
proposal ──► specs ──► design ──► tasks ──► implement
   why        what       how       steps      do it
```

どの段階にも戻れます。これらは「ゲート」ではなく、次へ進みやすくするための材料です。

**5. アーカイブすると、変更が仕様へ反映されます。** 作業が完了したら変更をアーカイブします。仕様差分はメイン仕様へマージされ、変更フォルダーは日付付きで `changes/archive/` に移動します。これで仕様は新しい現実を表し、次の変更に進めます。

## 全体像

```text
┌─────────────────────────────────────────────────────────────────┐
│                          openspec/                              │
│                                                                 │
│   ┌──────────────────┐         ┌──────────────────────────┐    │
│   │     specs/       │         │        changes/          │    │
│   │                  │ ◄─────  │                          │    │
│   │ source of truth  │  merge  │ one folder per change    │    │
│   │ how things work  │  on     │ proposal · design ·      │    │
│   │ today            │ archive │ tasks · delta specs      │    │
│   └──────────────────┘         └──────────────────────────┘    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

重要なのは 2 つのフォルダーです。`specs/` が現在の真実です。`changes/` は提案中の変更です。アーカイブによって、提案が仕様に取り込まれます。

## 実際のループ

デフォルト設定では、日々の流れは次のようになります。必要なら最初に探索し、次に計画を下書きし、確認してから実装し、最後に仕様へ反映します。

```text
/opsx:explore                   →  (optional) think it through with the AI first
/opsx:propose add-dark-mode     →  AI drafts proposal, specs, design, tasks
        (you read and adjust the plan)
/opsx:apply                     →  AI builds it, checking off tasks
/opsx:archive                   →  specs updated, change archived
```

**迷ったら、まず探索します。** `/opsx:explore` は、リスクなしで使える思考パートナーです。コードを読み、選択肢を整理し、成果物を作る前に曖昧なアイデアを具体的な計画へ近づけます。曖昧な指示から AI が「それらしい何か」を作ってしまうのを防ぐ、最も安いタイミングの安全策です。やりたいことが明確なら、直接 `/opsx:propose` に進んで構いません。Explore はデフォルトプロファイルに含まれているため、いつでも使えます。詳しくは [探索ガイド](explore.md) を参照してください。

これらは AI アシスタントのチャットに入力するスラッシュコマンドです。セットアップだけはターミナルで `openspec init` を実行します。この区別に慣れていない場合は、最初に [コマンドの仕組み](how-commands-work.md) を読んでください。最も混乱しやすいポイントです。

## 「ゲートではなくイネーブラー」

OpenSpec では、この表現をよく使います。意味は単純です。

古い仕様プロセスはウォーターフォールになりがちです。計画を完了してから実装が許可され、後戻りは重くなります。OpenSpec はその進め方を前提にしません。`proposal → specs → design → tasks` の順序は、次に何を「強制」するかではなく、次に何を「作りやすくするか」を表します。

実装中に設計が間違っていると気づいたら、`design.md` を編集して続けます。スコープを小さくすべきだと分かったら、提案を更新します。何もロックされません。依存関係は AI に必要な文脈を渡すためにあります。ユーザーを囲い込むためではありません。

この仕組みの強みは、実際の作業が反復的であることを隠さない点です。一方で、前進を強制するものはありません。変更を広げすぎず、1 つの目的に保つ責任は利用者側にあります。[ワークフロー](workflows.md) では、そのための実践的な進め方を紹介しています。

## 少しの手間をかける価値

OpenSpec は手順を 1 つ増やします。実装前に短い計画を書きます。その代わり、次の効果があります。

- **損失が大きくなる前に、方向違いに気づけます。** 1 段落の提案を直すのは安い作業です。AI が 400 行書いた後で前提の誤解を直すのは高くつきます。
- **計画とコードが同じリポジトリに残ります。** 6 か月後でも、仕様を見ればその動作になった理由が分かります。次の AI セッションにも同じ文脈を渡せます。
- **変更をレビューできます。** 変更フォルダーは小さなパッケージです。提案、仕様差分、タスクを順に確認できます。チャット履歴を掘り返す必要はありません。
- **既存コードベースに合います。** 差分方式なので、最初に全体を文書化しなくても、5 万行のアプリに対する変更を扱えます。

正直なトレードオフもあります。本当に些細な 1 行修正では、この形式が割に合わない場合があります。それで構いません。OpenSpec は軽量ですが、無料ではありません。合意が重要な変更で使ってください。AI は、曖昧な依頼でも自信を持って実装しがちだからです。
