# 用語集

OpenSpec の用語を 1 か所にまとめ、平易な言葉で定義しています。一度流し読みしておくと、残りのドキュメントを読みやすくなります。

用語はトピックごとにグループ化され、各グループ内でアルファベット順に並べられます。

## コア名詞

**仕様。** システムの一部がどのように動くかを説明する文書です。仕様は `openspec/specs/` にあり、ドメインごとに整理され、要件とシナリオで構成されます。「このソフトウェアは何をするのか？」に対する合意済みの答えです。詳しくは [コンセプト](concepts.md#specs) を参照してください。

**真実の情報源。** `openspec/specs/` ディレクトリ全体です。ここには、現在合意されているシステムの振る舞いが保持されます。変更はそこへの編集を提案し、アーカイブ時に適用されます。

**変更。** 1 つの作業単位です。`openspec/changes/<name>/` 配下のフォルダーとして管理されます。変更には、提案、設計、タスク、導入される仕様編集など、その作業に関するものがすべて含まれます。1 つの変更は、1 つの機能または修正に対応します。

**アーティファクト。** 変更内のドキュメントです。標準的な成果物は、提案、仕様差分、設計、タスクです。これらは依存関係の順序で作成され、相互に影響します。

**仕様差分。** 仕様全体を再説明するのではなく、`ADDED`、`MODIFIED`、`REMOVED` セクションで変更内容だけを説明する、変更内の仕様です。これにより、OpenSpec は既存システムへの変更を扱いやすくします。詳しくは [コンセプト](concepts.md#delta-specs) を参照してください。

**ドメイン。** 仕様の論理グループです（`auth/`、`payments/`、`ui/` など）。チームがシステムをどう捉えているかに合うドメインを選びます。

## 仕様の内部

**要件。** システムが満たすべき 1 つの振る舞いです。通常は RFC 2119 キーワードを使って、「システムは 30 分の非アクティブ状態後にセッションを期限切れにするものとする（SHALL）」のように書きます。要件には *方法* ではなく、*何を* するかを書きます。

**シナリオ。** 実際の要件の具体的でテスト可能な例。通常、Given/When/Then 形式で示されます。シナリオによって要件が検証可能になります。シナリオから自動テストを作成できます。

**RFC 2119 のキーワード。** MUST、SHALL、SHOULD、MAY には、要件の強さに関する標準化された意味があります。MUST と SHALL は必須、SHOULD は正当な例外を許す推奨、MAY は任意です。この名前は、それらを定義したインターネット標準文書に由来します。

## アーティファクト

**提案 (`proposal.md`)。** 変更の *なぜ* と *何を*: その意図、範囲、および高レベルのアプローチ。最初に作成するアーティファクト。

**設計 (`design.md`)。** *方法* を説明します。技術的アプローチ、アーキテクチャ上の判断、触る予定のファイルなどです。単純な変更では省略できます。

**タスク (`tasks.md`)。** チェックボックス付きの実装チェックリストです。AI は `/opsx:apply` 中にこれを処理し、進行に合わせて項目にチェックを入れます。

## ライフサイクル

**アーカイブ。** 変更を完了する操作です。仕様差分はメイン仕様へマージされ、変更フォルダーは `openspec/changes/archive/YYYY-MM-DD-<name>/` に移動します。アーカイブ後、仕様は新しい現実を表します。詳しくは [コンセプト](concepts.md#archive) を参照してください。

**同期。** 変更をアーカイブせずに、変更の仕様差分をメイン仕様へマージします。通常は自動で行われます（アーカイブ時に実行が提案されます）が、長期の変更では `/opsx:sync` として単独で使えます。詳しくは [コマンド](commands.md#opsxsync) を参照してください。

## ワークフローとコマンド

**OPSX.** 現在の標準的な OpenSpec ワークフローです。厳格なフェーズではなく、流動的なアクションを中心に構成されています。スラッシュコマンドはすべて `/opsx:` で始まります。詳しくは [OPSX ワークフロー](opsx.md) を参照してください。

**スラッシュコマンド。** AI アシスタントのチャットに入力するコマンドです（例: `/opsx:propose`）。ワークフローを進めるために使います。ターミナルコマンドではありません。詳しくは [コマンドの仕組み](how-commands-work.md) を参照してください。

**Explore (`/opsx:explore`).** 思考パートナーとして使うコマンドです。コードベースを読み、選択肢を比較し、曖昧なアイデアを具体的な計画へ近づけます。アーティファクトもコードも作りません。問題はあるが計画がまだない場合の推奨スタート地点です。詳しくは [まずは探索する](explore.md) を参照してください。

**CLI.** ターミナルで実行する `openspec` プログラムです。プロジェクトの設定、変更の一覧表示と検証、ダッシュボード表示、アーカイブを行います。詳しくは [CLI](cli.md) を参照してください。

**スキル。** AI アシスタントが自動検出して従う指示のフォルダー (`.../skills/openspec-*/SKILL.md`)。スキルは、OpenSpec ワークフローをアシスタントに提供するための新たなクロスツール標準です。

**コマンドファイル。** ツールごとのスラッシュコマンドファイルです（`.../commands/opsx-*`）。スキルと並んで、従来の配信方式として引き続きサポートされています。通常、直接触る必要はありません。

**プロファイル。** プロジェクトにインストールするスラッシュコマンドのセット。**core**（デフォルト）は `propose`、`explore`、`apply`、`update`、`sync`、`archive` を含みます。**expanded** セットでは `new`、`continue`、`ff`、`verify`、`bulk-archive`、`onboard` も利用できます。変更するには `openspec config profile` を実行します。

**配信。** OpenSpec がツールにスキル、コマンドファイル、またはその両方をインストールするかを表す設定です。グローバル設定で管理し、`openspec update` で適用します。

## カスタマイズ

**スキーマ。** ワークフローで作るアーティファクトと、その依存関係を定義するもの。組み込みのデフォルトは `spec-driven`（提案 → 仕様 → 設計 → タスク）です。既存スキーマを複製して調整することも、独自に作成することもできます。詳しくは [カスタマイズ](customization.md#custom-schemas) を参照してください。

**テンプレート。** 特定のアーティファクトに対して AI が生成する内容を形作る、スキーマ内の Markdown ファイルです。テンプレートを編集すると、再構築せずに AI の出力へ反映されます。

**プロジェクト設定 (`openspec/config.yaml`)。** プロジェクトごとの設定です。デフォルトスキーマ、すべての計画リクエストへ挿入される `context:`、アーティファクトごとの `rules:` を指定できます。OpenSpec にスタックや規約を伝える最も簡単な方法です。詳しくは [カスタマイズ](customization.md#project-configuration) を参照してください。

**コンテキスト注入。** プロジェクトの背景情報を `config.yaml` の `context:` フィールドに書き、AI が生成するすべてのアーティファクトへ自動的に追加する仕組みです。AI が別ファイルを毎回読んでくれることを期待するより安定します。

**依存関係グラフ。** アーティファクトの `requires:` 関係によって形成される有向グラフです。これは DAG（有向非循環グラフ: 矢印が前方だけを指し、ループしないグラフ）であり、OpenSpec はこれを使って次に何を作成できるかを判断します。

**ゲートではなくイネーブラー。** アーティファクトの依存関係は、次に何が *必須* かではなく、次に何が *可能* になるかを示すという考え方です。いつでもアーティファクトに戻って編集できます。詳しくは [コアコンセプトの概要](overview.md#ゲートではなくイネーブラー) を参照してください。

## リポジトリ間の調整 (ベータ版)

このセクションは、計画が複数のリポジトリにまたがる場合だけ関係します。ベータ版なので、多くのユーザーは無視して構いません。詳しくは [ストアユーザーガイド](stores-beta/user-guide.md) を参照してください。

**ストア。** 計画全体を扱う独立したリポジトリです。通常の `openspec/` 構造（仕様と変更）に加えて、小さな ID ファイルを持ちます。一度マシンに名前で登録すると、どこからでも OpenSpec コマンドで参照できます。

**参照。** コードリポジトリの `openspec/config.yaml` に書く、利用するストアの宣言です。参照は読み取り専用です。リポジトリは自分自身のルートを保持し、`openspec instructions` は参照先ストアの仕様インデックスを取得します。各項目には、その仕様を取得するための正確なコマンドが含まれます。

**作業コンテキスト。** `openspec context` が現在のリポジトリ向けにまとめる情報です。対象の OpenSpec ルート、参照先ストア、各ストアから情報を取得する方法が含まれます。「今どの前提で作業しているのか？」への答えです。

**ワークセット。** 一緒に開きたいフォルダーをまとめた、個人用・端末ローカルのセットです。作業対象のコードリポジトリや関連ストアをまとめて扱うために、`openspec workset create` で明示的に作成します。これらのローカルパスは共有の計画リポジトリにはコミットされません。
