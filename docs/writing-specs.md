# 適切な仕様を書く

白紙のページから仕様書を書くことはほとんどありません。あなたはわかりやすい言葉で変更を説明し、`/opsx:propose` が要件とシナリオの草案を作成し、それを適切なものに仕上げます。このページでは、最後の部分、つまり「良い」とはどのようなものなのか、AI をそこに導く方法について説明します。

これは [変更のレビュー](reviewing-changes.md) と対になるページです。レビューは下書きの弱点を見つける作業であり、良い仕様を書くには「強い要件とは何か」を知っておく必要があります。

## 仕様はコードではなく動作です

仕様には、システムがどのように構築されているかではなく、誰でも確認できる観点から、システムが「何をする」のかが記載されています。これは、**要件** (行動の記述) と **シナリオ** (それを証明する具体的な例) で構成されます。

```markdown
### Requirement: セッションタイムアウト
システムは 30 分間操作がなければセッションを期限切れにしなければならない（SHALL）。

#### Scenario: アイドルタイムアウト
- GIVEN 認証済みセッション
- WHEN 操作のない状態が 30 分続く
- THEN セッションが無効化され、ユーザーに再認証を求める
```

*方法* (キュー、ライブラリ、テーブル スキーマ) を `design.md` またはコードに保持します。動作と実装が 1 つの要件に混在すると、その要件はテストできなくなり、コードが変更された瞬間から古くなり始めます。

## 適切な要件とは

適切な要件とは、他の人に渡してテストできるように明確に記載された 1 つの動作です。

- **1 つのステートメント、1 つの `SHALL`/`MUST`。** 要件に 3 つの「and also」句がある場合、実際には 3 つの要件になります。分割してください。
- **観察可能** コードの外部にいる人は、それが成り立つかどうかを知ることができるはずです。 「アップロードが 10 MB を超えると、システムはエラー バナーを表示するものとします」という記述が確認できます。 「システムは大規模なアップロードを適切に処理するものとします」はそうではありません。
- **適切な強度。** OpenSpec は RFC 2119 キーワードを使用しますが、これらは異なる意味を持ちます。

|キーワード |意味 |
  |---------|---------|
| `MUST` / `SHALL` | 必須要件。原則として交渉不可。 |
| `SHOULD` | 正当な例外を許す強い推奨。 |
| `MAY` | 任意の選択肢。 |

デフォルトでは、`MUST`/`SHALL` に到達します。 `SHOULD` は、本当に「そうしない正当な理由がない限り」という場合にのみ使用してください。

要件のテスト: *コードを一度も見たことがないテスターは、コードが合格したかどうかを判断できますか?* そうでない場合は、コードをシャープにする必要があります。

## 良いシナリオとは何か

シナリオは、要件が維持される場所です。それぞれが具体的な GIVEN / WHEN / THEN であり、自動テストになる可能性があります。

- **その要件を実行します。** 要件を言い換えるだけのシナリオ、つまり何もテストしません。特定の結果を伴う特定の状況にします。
- **正常系だけでなく、重要なケースもカバーします。** 有効なログインだけなら簡単です。空入力、期限切れトークン、二重クリック、障害発生時など、バグは例外的な状況に潜みます。そうした場面ほどシナリオの価値があります。
- **タイトルにケースの名前を付けます。** 「シナリオ: 期限切れのトークンを拒否する」では、レビュー担当者に何がカバーされているかが一目でわかります。 「シナリオ: テスト 2」ではそうではありません。

役立つ習慣: 承認する前に、*壊れたら腹が立つケースは何ですか?* と尋ね、シナリオでその名前が挙げられていることを確認してください。

## 適切な種類のデルタを選択してください

変更は、仕様に対する編集を 3 つのセクション タイプで説明します。適切なものを使用すると、アーカイブされた仕様が正確に保たれます。

- **`## ADDED Requirements`** — 以前には存在しなかったまったく新しい動作。
- **`## MODIFIED Requirements`** — すでに存在し、変更されている動作。完全な新しいバージョンを含めます。変更点に関する短いメモはレビュー担当者に役立ちます。
- **`## REMOVED Requirements`** — 行動がなくなり、その理由が示されます。

アーカイブ時、ADDED は本仕様へ追加され、MODIFIED は旧版を置き換え、REMOVED は本仕様から取り除かれます。capability の最後の要件を削除すると、その capability は廃止されます。中身のない仕様を残す代わりに、archive は `openspec/specs/<capability>/spec.md` を削除します。これはファイルを削除する唯一のアーカイブ処理であるため、明示的な指定が必要です。変更の `.openspec.yaml` に、このファイルで必要な `schema:` と並べて `retire_capabilities: true` を追加してください。指定がなければ archive は中止し、その旨を伝えます。呼出元のチェックアウト内にある仕様では、アーカイブ出力にコミット済みファイルを復元する `git checkout` も表示されます。選択済み store にはチェックアウトの範囲に即した復旧方法を案内します。既存の変更を ADDED として記述すると競合する要件が2つ生じ、新しい振る舞いを MODIFIED として記述すると置き換える対象がありません。迷ったら現在の仕様を開き、要件がすでにあるか確認してください。

もう1つ知っておくべきセクションがあります。delta でまだ存在しない capability を作る場合は、capability の目的を1〜2文で書いた `## Purpose` から始めます。archive はこれを作成する本仕様の Purpose として使用します。省略すると手作業で埋める `TBD` プレースホルダーが残ります。既存仕様にはすでに Purpose があるため、delta 側の Purpose は無視されます。変更するには `openspec/specs/<capability-path>/spec.md` を直接編集してください。ここで `<capability-path>` は `specs/` からの相対ディレクトリです。フラットなプロジェクトの `user-auth` や、ドメイン別に構成したプロジェクトの `identity/user-auth` などが該当します。

## 変更のサイズを適切に調整する

最も一般的なオーサリングの間違いの 1 つは、要件の言葉遣いが悪いことではありません。それは、3 つの変更を加えようとする変更です。

**良い変更には、一文で言える 1 つの意図があります。** 「ダークモードの切り替えを追加する」。 「ログインエンドポイントのレート制限を行います。」 「セッションを Cookie から移行します。」変更の説明に多くの「および」が必要な場合、それは変更を分割する合図です。

変更が大きすぎる兆候:

- 提案の範囲は、無関係な機能のリストのように見えます。
- レビューには午後かかるので、誰もレビューしません。
- 2 人で作業すると衝突せずに作業できませんでした。
- タスクの半分は単独で出荷できます。

小さな変更はレビューしやすく、集中した 1 セッションで実装しやすく、半年後にアーカイブを読み返したときにも理解しやすくなります。必要なら複数の変更を並行して進められます。詳しくは [変更の編集と反復](editing-changes.md) と [ワークフロー](workflows.md) を参照してください。

逆もあります。1 行のタイプミス修正に、3 つの要件と設計ドキュメントは必要ありません。手続きの重さは、変更のリスクに合わせてください。

## AI を良いドラフトに導く方法

`/opsx:propose` が最初のドラフトを作成するため、返されるものの品質は、提供されたものの品質を追跡します。要件を手動で記述する必要はありません。AI を適切に制御する必要があります。

- **意図と境界を述べます。** *「最初の読み込み時に OS 設定に従うダークモードの切り替えを追加します。既存のテーマ API には触れないでください。」* 範囲外の半分は、範囲内の半分と同じくらい重要です。
- **関心のあるケースに名前を付けてください。** *「すでにテーマを手動で選択しているユーザー向けのシナリオがあることを確認してください。」* AI は、ユーザーが指定した内容をカバーします。
- **その後で編集します。** 仕様はただの Markdown です。あいまいな `SHALL` を具体化し、何も検証していないシナリオを削除し、抜けているケースを追加してください。AI に依頼するなら、たとえば *「タイムアウト要件があいまいなので、30 分に固定してください。」* のように伝えます。

下書き、シャープ化、繰り返し。それを数回繰り返すことで、信頼できる仕様が得られます。これが重要です。

## 簡単なチェックリスト

- [ ] 各要件は、`SHALL`/`MUST` で観察可能な 1 つの動作です。
- [ ] 実装の詳細は要件に組み込まれていません。
- [ ] すべての要件には、それを実際に実行するシナリオが少なくとも 1 つあります。
- [ ] 重要なエッジケースやエラーケースにも、正常系だけでなくシナリオがあります。
- [ ] デルタは、現在の仕様に対して正しく ADDED / MODIFIED / REMOVED を使用します。
- [ ] 変更全体には、文で述べることができる 1 つの意図があります。
