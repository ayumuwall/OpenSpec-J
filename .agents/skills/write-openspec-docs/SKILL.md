# OpenSpec ドキュメントを書く

OpenSpec の利用者向けドキュメントを執筆します。[writing.md](writing.md)を読んでください。ここで執筆するすべての内容について、同ファイルを文体の基準とします。すぐに適用する要点は次のとおりです。

- ページは情報を探すための画面であり、随筆ではありません。読者が答えを見つけられるかは構成で決まり、文章は読み心地だけを決めます。各節の冒頭に答えを置き、物語のように順を追って説明しないでください。
- アウトラインの前にページの種類を決めます。ガイドは読者の作業に沿って構成します。リファレンスは製品の構造を反映し、正確なフィールド名、コマンド名、ファイル名を拾い読みの目印にします。リファレンスでは、複数の事実を 1 つの文、セル、段落へ詰め込まず、契約全体を網羅します。
- 答えになる最短の版を下書きします。簡潔なページを拡充するのは容易ですが、肥大化したページの削減は書き直しになります。平易な言葉を必要最小限だけ使い、1 行で収まる考えは 1 行で書いてください。多くの読者が読み飛ばす詳細はリンク先へ置き、実用情報（コマンド、実際の出力、失敗と解決方法）は省略しません。
- 文は単純に、構成は賢くします。主語、動詞、目的語を使い、実際に起きることをそのまま示す明快な文を書いてください。余分な事実を詰め込んだり、独自の切り口を加えたりしません。誇張する形容詞、前置き、em ダッシュは使いません。
- 1 つの場所には 1 つの役割だけを持たせます。1 文に 1 つの事実を書き、リストの導入文はリストの内容だけを告知し、1 節では読者の質問または検索対象を 1 つだけ扱います。関連する事実にも専用の場所を与え、ほかの事実へ便乗させません。
- 読者が検証できるものを根拠にします。パスまたはフォルダを先に示し、概念はその説明として添え、実際の出力を正確に掲載します。
- 共通テンプレートはありません。一覧ページは全項目を示すリストから始め、その後で各項目を独立した単位として説明します。リスト内へ説明を詰め込みません。手順には番号を付けます。番号は順序を表し、項目一覧には箇条書きを使います。1 つの考えや理由の説明には、短い文章を使います。
- 重要な事実はすべて、拾い読みできる目印へ置きます。コードフェンス、番号付きの太字導入、`**用語**：事実`形式の箇条書き、表、ファイルツリーのいずれかです。段落の途中だけに置いてはいけません。
- 完了前に 2 つの最終テストを行います。検索可能性テストでは、各質問や正確な製品名を拾い読みだけで見つけられるか確認します。一覧性テストでは、レンダリングしたページを形として眺め、読み切れそうか、作業のように見えるかを確認します。表を大きく変更した場合は、デスクトップ幅と狭い幅の両方で確認してください。失敗した場合は、必要性のない記述が追加されています。レビューへ残さず、その場で修正します。

## 基本規則

- 執筆前に`no-ai-slop`スキルを読み込みます。一般的な冗長表現は同スキルが扱い、OpenSpec ドキュメント固有の見た目と文体は[writing.md](writing.md)が扱います。
- 編集前に対象ページを最初から最後まで読みます。
- ソースに存在する事実だけを書きます。フラグ、パス、出力を正確に記載してください。簡単に確認できない記述も書いて構いませんが、作業報告では未確認と明記します。もっともらしい文で不足を埋めてはいけません。
- 1 つの事実を説明するページは 1 つだけです。ほかの場所からはそのページへリンクします。ドキュメントツリーの README がページマップと構造上の不変条件を管理します。構成変更やページ追加の前に確認してください。
- リファレンスページでは、文章を書く前にソースから契約を一覧化します。[writing.md](writing.md#reference-pages)のリファレンス手順に従ってください。
- 拾い読みのしやすさや文体に迷った場合は、手本に合わせます。節の構成と一覧には`docs-lab/start/setup.md`、複数手順の作業には`docs-lab/start/installation.md`の「アンインストール」を参照してください。

## 完了時

変更内容と未確認の記述を利用者へ示します。

利用者が、すべてのコマンドを実行し、1 回の作業で 1 節だけを書き、正式なチェックポイントを設ける、証拠優先の詳細な執筆セッションを求めた場合は、[full-process.md](full-process.md)に従ってください。
