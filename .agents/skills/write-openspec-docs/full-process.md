# 詳細な執筆プロセス（任意）

証拠を優先し、チェックポイントを設けてページを執筆する方法です。利用者が詳細なプロセスを求めた場合だけ使用します。既定モードでは SKILL.md だけを使用します。

## 準備する（各セッションの執筆前）

1. 執筆対象が属するドキュメントツリーのルートにある README を読みます。README に不変条件またはページマップが記載されている場合は、このスキルより優先します。
2. 対象ページを最初から最後まで読み、コメントから参照されている内容も確認します。
3. 対象ページからリンクするページや内容が重なる同列ページを読みます。説明へ取り込まずリンクのまま残す内容を判断できる範囲まで確認してください。
4. ページの役割を 1 行で記載します。どの読者が、何をしようとして訪れ、読後に何ができるようになるかを示してください。ページに役割を示す文がある場合は、その文と照合します。docs-lab ページでは、タイトル直下の`>`引用が該当します。これから書く単位がその役割を果たさない場合は、無理に執筆せず停止して問題を提示します。

## 小さな単位で進める

- 既定の単位は 1 つの`##`節です。1 ページを 1 回で書かず、複数回に分けます。
- 既存の文章を修正する場合は、見出しをいくつまたいでも、依頼された変更を 1 単位とします。
- 利用者が現在の単位をレビューした後にだけ、次の単位を執筆します。修正を求められた場合は、その修正だけを行い、次の単位を紛れ込ませないでください。

## 文章の前に証拠を確認する

単位を執筆する前に、記述の根拠を把握します。

- 掲載するターミナルコマンドを低コストで実行できる場合は実行します。読み取り専用コマンドは任意の場所で、状態を変更するコマンドは作業用ディレクトリだけで実行します。実行できない場合は実行しません。実際の出力を貼り付け、不要部分の省略だけを行います。出力を書き換えてはいけません。
- 名前をソースと照合します。フラグ、パス、設定キー、既定値は、旧ドキュメントではなく`src/`と CLI 自身のヘルプから取得します。ドキュメントとソースが一致しない場合はソースを正とし、相違を利用者へ伝えます。
- もっともらしい文で不足を埋めてはいけません。確認できなかった記述は、黙って公開せずチェックポイントで明示します。高コストな確認が 1 つあっても、下書き全体を止めないでください。

## 冗長表現を取り除く

下書きした単位に`no-ai-slop`スキルを適用し、その編集結果を反映します。ドキュメントの文章も例外ではありません。同スキルが示すパターンは、このドキュメントが信頼を得るべき読者に機械的な文章と受け取られます。

## 役割を果たしているか確認する

役割を示す文で想定した読者として、実際の問題を抱えて初めて訪れたつもりで単位を読み直します。次の 3 点を確認してください。

1. 読者が実行できるか。すべての手順を記載どおりに実行でき、ページ内で説明もリンクもしていない知識へ依存していないことを確認します。
2. 成功したと判断できるか。成功したか不明になり得る場合は、出力、ファイル、エージェントの次の動作など、目に見える結果を示します。結果が明白な場合は、成功を示す文を追加する必要はありません。
3. 読者が以前はできなかった何をできるようになったか。正直な答えが「背景を読んだ」だけなら、問題を解決せず説明しているだけです。役割を果たす内容まで削るか、利用者へ問題を提示します。

この確認に通らない単位は、注釈を付けるのではなく、チェックポイントの前に修正します。

## チェックポイント

単位の最後に、利用者へ次の内容を示します。

- ファイルパスと執筆した単位
- ページの役割を示す 1 行と、その役割に向けて、この単位によって読者ができるようになること
- 確認した記述と確認方法（実行したコマンド、読んだファイル）
- 未確認の記述

その後、停止します。利用者から指示があったときに次の単位を開始します。
